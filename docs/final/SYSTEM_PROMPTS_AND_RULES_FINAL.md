# Финальные системные инструкции и программные правила

**Проект:** «ИИ-ассистент по внутренним заявкам на закупку»
**Версия:** MVP 1.0
**Дата фиксации:** 4 августа 2026 года

## 1. Главный вывод

В приложении нет единого «магического промпта», который управляет всей закупкой. Рабочая архитектура использует:

1. отдельные инструкции структурированного извлечения для оформления заявки;
2. отдельные инструкции Regulation Q&A для ответа по базе знаний;
3. схемы структурированного ответа;
4. программные нормализаторы, валидаторы, правила категорий, полноты и жизненного цикла;
5. транзакционные операции PostgreSQL/Supabase.

LLM помогает понять и сформулировать. Критические решения о заявке принимает код либо пользователь явным подтверждением.

## 2. Intake / extraction — оформление заявки

### 2.1. Фактический источник инструкций

Авторитетная рабочая инструкция хранится в:

`app/extraction/prompts/approval_context_extraction.md`

Несмотря на историческое имя файла, он содержит как правила извлечения контекста предварительного согласования, так и отдельный раздел **Intake-поля для Telegram**. К инструкции программно добавляется компактный справочник допустимых категорий.

По умолчанию используется модель `gpt-5.6-luna` через OpenAI Responses API и Structured Outputs. Telegram использует режим `hybrid`, если ключ OpenAI доступен; без ключа применяется консервативный программный режим `rule`.

### 2.2. Роль модели

Модель получает пользовательский текст либо JSON с полями:

- `user_message` — новое сообщение;
- `confirmed_context` — ранее подтверждённые данные;
- `current_question` — текущий вопрос;
- `awaiting_field` — ожидаемое поле.

Она должна извлечь только сведения, явно присутствующие в новом сообщении, и вернуть типизированный объект. Контекст нужен для понимания короткого ответа, но не разрешает повторно выдавать старое значение как новое без подтверждения пользователя.

### 2.3. Формат Structured Outputs

Схема требует все поля верхнего уровня. Основные группы:

- тип закупки, категория и предмет;
- количество, единица и характеристики;
- результат услуги;
- сумма, модификатор суммы, валюта и период оплаты;
- бюджетный статус;
- срок, место, цель, подразделение и контакт;
- признаки срочности, единственного поставщика, доступа к данным и работ на объекте;
- `confidence_items` — уверенность по полям от 0 до 1;
- `evidence_items` — короткий дословный фрагмент пользовательского текста для каждого извлечённого поля;
- `unknown_fields` — отсутствующие сведения;
- `contradictions` — явные противоречия.

Отсутствующие строки и логические значения возвращаются как `null`, массивы — как пустые массивы. Категория допускается только из G01–G15 или S01–S15 и должна соответствовать типу закупки.

### 2.4. Основные рабочие инструкции intake

Модель обязана:

- не вычислять маршрут, диапазон правила или согласующих;
- не считать заявку согласованной или зарегистрированной;
- отделять сумму от бюджетного статуса: «бюджет 180 тысяч» сообщает сумму, но не доказывает `budgeted`;
- не считать бренд признаком единственного поставщика;
- трактовать «срочно» только как заявление срочности, не назначая P1–P4 без явного кода;
- выбирать категорию только из переданного справочника, а при неоднозначности возвращать `null`;
- подтверждать извлечённые поля короткими фрагментами исходного сообщения;
- фиксировать явные противоречия;
- различать товар и услугу по действию: «купить шкаф» — товар, «собрать шкаф» — услуга;
- давать предмету короткое естественное название, не копировать туда всё сообщение;
- не дублировать предмет услуги как ожидаемый результат;
- для нескольких объектов услуги не складывать количества разных объектов;
- для нескольких товарных позиций не сворачивать их в одно общее количество;
- в конструкции «3 канистры по 10 литров» извлекать 3 позиции, а объём одной позиции помещать в характеристики;
- возвращать выражение даты дословно, а не придумывать ISO-дату;
- не выдумывать место, цель, подразделение, контакт или бюджетный статус;
- не формировать пользовательский ответ.

### 2.5. Проверки после модели

Structured output не принимается автоматически. Приложение:

- проверяет JSON schema и запрещает лишние поля;
- проверяет наличие evidence в исходном сообщении;
- отклоняет или очищает значения без подтверждения;
- нормализует сумму, дату, единицу, количество и бюджетный статус;
- сопоставляет категорию с реальным классификатором;
- не заменяет точное программное извлечение менее точным вариантом модели;
- при временной ошибке OpenAI в `hybrid` использует резервный программный разбор.

## 3. Regulation Q&A — вопросы по регламентам

### 3.1. Фактический источник инструкций

Авторитетная рабочая инструкция хранится в:

`app/rag/prompts/regulation_qa.md`

Модель по умолчанию — `gpt-5.6-luna`. Вход — JSON с `question` и массивом `context`. Каждый элемент контекста содержит идентификатор фрагмента, название и тип документа, `source_kind`, путь раздела и текст.

До модели приложение выполняет гибридный поиск: embeddings `text-embedding-3-small`, русский полнотекстовый поиск и объединение RRF. Модели передаются пять лучших фрагментов.

### 3.2. Формат Structured Outputs

Модель возвращает:

- итоговый `answer`;
- короткие проверяемые `claims`;
- для каждого утверждения — `cited_chunk_ids` только тех фрагментов, которые прямо его подтверждают;
- `insufficient_context`;
- `source_conflict` и краткое описание противоречия;
- обязательные служебные поля схемы.

Текст каждого утверждения должен дословно входить в итоговый ответ. Технические идентификаторы и оценки поиска пользователю не показываются.

### 3.3. Основные рабочие инструкции Regulation Q&A

Модель обязана:

- отвечать только по переданному контексту и не использовать внешние знания;
- не придумывать лимиты, сроки, статусы, согласующих или обязательные поля;
- при недостаточном контексте устанавливать `insufficient_context=true`;
- при противоречии источников устанавливать `source_conflict=true`;
- отвечать по-русски: сначала прямой ответ, затем краткое пояснение;
- не цитировать длинные фрагменты;
- привязывать каждое утверждение только к непосредственно подтверждающим фрагментам;
- различать нормативный источник, инструкцию, FAQ, пример и шаблон;
- не переносить числа, даты, адреса, суммы, марки, имена и подразделения из примеров или шаблонов в пользовательский случай;
- использовать пример/шаблон только для перечня полей или явно помеченного абстрактного примера по прямой просьбе;
- сохранять пользовательские суммы и сроки как данные вопроса;
- не выполнять арифметику маршрута самостоятельно;
- отвечать на все аспекты составного вопроса отдельными утверждениями;
- не требовать сумму или дату для общего вопроса о правиле, если правило найдено;
- считать разные положительные формулировки наличия бюджета одним условием, не смешивая их с отрицанием или неизвестным статусом.

### 3.4. Программная проверка ответа

После модели приложение проверяет:

- что все указанные `chunk_id` реально были переданы модели;
- что каждый источник допустим для данного утверждения;
- что пример или шаблон не используется как нормативное доказательство пользовательского факта;
- что конкретные значения присутствуют в вопросе или подтверждающем документе;
- что ответ не слишком длинный и не содержит неподтверждённых утверждений;
- что числовой диапазон и продолжительность рассчитаны программным модулем, когда вопрос зависит от порога;
- что при ошибке возможна одна управляемая попытка исправления ответа;
- что при невозможности подтверждения возвращается контролируемый отказ.

## 4. Решения детерминированного кода

Ниже перечислены решения, которые LLM не принимает.

### 4.1. Поля и полнота

- допустимые названия, типы и перечисления полей;
- обязательные поля по типу и категории;
- валидность количества, даты, суммы и единицы;
- приоритет явно подтверждённого значения;
- обнаружение конфликта и необходимость повторного уточнения;
- готовность карточки;
- выбор следующего вопроса.

### 4.2. Категории

- список реальных категорий;
- сопоставление точного кода, номера, полного и частичного названия;
- хранение 2–4 кандидатов;
- запрет ожидания номера до показа списка;
- защита от повторяющихся циклов;
- допустимость выбранной категории для товара или услуги.

### 4.3. Жизненный цикл заявки

- правило одного активного черновика;
- версии состояния и защита от устаревшей записи;
- идемпотентность повторной команды;
- допустимость подтверждения, редактирования и отмены;
- запрет регистрации по свободному тексту;
- уникальная нумерация через PostgreSQL sequence;
- статус `draft`, `new` или `cancelled`;
- право владельца читать и изменять заявку;
- состав финального снимка зарегистрированной заявки.

### 4.4. Предварительный маршрут согласования

- выбор диапазона суммы;
- различие `budgeted` и `unbudgeted`;
- дополнительные правила срочности, единственного поставщика, категории S11, доступа к данным и работы на объекте;
- требование уточнить неизвестный бюджетный статус;
- формирование предварительного списка ролей.

Модуль не выполняет согласование и не принимает решение за уполномоченного сотрудника.

### 4.5. Поиск и подтверждение источников

- подготовка поисковых запросов;
- векторный и полнотекстовый поиск;
- RRF и выбор пяти фрагментов;
- фильтрация активных версий;
- классификация типа источника;
- проверка идентификаторов и конкретных значений;
- контролируемый отказ;
- срок жизни контекста уточнения — 30 минут и не более трёх шагов.

## 5. Ограничения инструкций и архитектуры

- качество LLM не гарантирует корректность на любом будущем сообщении;
- без OpenAI Telegram переходит на ограниченное программное извлечение, а ответы по регламенту недоступны;
- одна заявка не поддерживает построчную спецификацию нескольких позиций;
- универсальное разделение смешанных потребностей не гарантируется;
- общий текст может дать слишком широкий список категорий;
- контекст уточнения Regulation Q&A обновляется неатомарно;
- база знаний учебная и не содержит внешних актуальных данных;
- модель не должна и технически не может завершить юридически значимое действие.

## 6. Правила изменения рабочих инструкций

1. Изменять инструкции только вместе со схемой и тестами соответствующего контура.
2. Не добавлять в prompt бизнес-решение, если оно должно быть проверяемым программным правилом.
3. Не вставлять секреты, персональные данные или реальные коммерческие условия в примеры.
4. После изменения intake повторять extraction/conversation-наборы и ручной сценарий Telegram.
5. После изменения Regulation Q&A повторять Production, Holdout, Blind и Conversation-наборы, проверять перенос значений из примеров и неподтверждённые конкретные значения.
6. Версию инструкции фиксировать вместе с версией приложения; не редактировать рабочий файл без записи причины изменения.

## 7. Итог

Финальные рабочие инструкции являются двумя специализированными контрактами, а не универсальным текстом. Надёжность MVP обеспечивается совместной работой инструкций, Structured Outputs, программной валидации, детерминированных бизнес-правил, транзакций базы данных и явного подтверждения пользователя.

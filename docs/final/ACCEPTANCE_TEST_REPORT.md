# Отчёт о приёмочном тестировании MVP

**Проект:** «ИИ-ассистент по внутренним заявкам на закупку»

**Интерфейс:** Telegram-бот «Закупкин»

**Дата финальной фиксации:** 15 августа 2026 года

**Production release:** `06f66e2906e48d46dec42a09a4f459bd1dd01593`

**Статус:** **MVP принят по результатам финального функционального и production smoke testing с известными ограничениями.**

## 1. Назначение и границы отчёта

Документ фиксирует итог приёмки учебного MVP после двух rehearsal-циклов,
стабилизации, синхронизации базы знаний и финальной проверки в production.
Проверялись два пользовательских контура:

- оформление и регистрация заявки на товар или услугу с сохраняемым черновиком;
- Regulation Q&A — ответы по внутренним регламентам с источниками и
  многошаговыми уточнениями.

Приёмка подтверждает функциональный объём выпускного проекта и не является
доказательством промышленной надёжности, универсальной точности или готовности
к эксплуатации на предприятии без дополнительного пилота и security review.
Полные продуктовые границы приведены в
[`FINAL_TECHNICAL_SPECIFICATION.md`](FINAL_TECHNICAL_SPECIFICATION.md).

## 2. Этапы приёмки и стабилизации

### 2.1. Initial acceptance / rehearsal

Первоначальные проверки выявили серьёзные дефекты, поэтому ранний статус
готовности был отозван. Основные классы проблем относились к:

- нормализации количества, единиц и суммы;
- смешанным потребностям «товар + услуга»;
- небезопасному общему fallback категорий;
- семантически несовместимым значениям высокозначимых полей;
- domain/intent-определению Regulation Q&A;
- сохраняемому состоянию диалога;
- пробелам классификации категорий.

Исторические причины и ход анализа сохранены в
[`../technical/REHEARSAL_FAILURE_ANALYSIS.md`](../technical/REHEARSAL_FAILURE_ANALYSIS.md)
и
[`../technical/REHEARSAL_2_FAILURE_ANALYSIS.md`](../technical/REHEARSAL_2_FAILURE_ANALYSIS.md).

### 2.2. Stabilization

В ходе стабилизации реализованы:

- provenance и readiness-защита категорий;
- гибридная deterministic + LLM классификация в закрытой taxonomy;
- обязательное подтверждение LLM-предложения пользователем;
- накопленный семантический контекст категории и его fingerprint;
- исправления hybrid-определения `procurement_type`;
- taxonomy `intake-categories-v3`;
- отдельный Regulation intent для вопросов о категориях;
- безопасное повторное использование подтверждённой категории при неизменном
  контексте;
- безопасное перемещение content-based UUID при обновлении индекса базы знаний.

### 2.3. Final verification

После исправлений:

- полный локальный regression suite завершился без ошибок;
- release `06f66e2906e48d46dec42a09a4f459bd1dd01593` успешно развёрнут;
- production working tree остался чистым;
- `purchasing-ai-bot.service` активен, Telegram polling запущен, startup logs
  не содержат ошибок запуска;
- индекс базы знаний синхронизирован: 14 активных документов, 118 чанков и
  118 embeddings, чанков без embedding нет;
- финальный Telegram smoke завершён успешно на перечисленных ниже сценариях.

## 3. Автоматические проверки

Финальный локальный baseline перед последним release:

| Набор / проверка | Результат |
|---|---:|
| Полный `pytest` | 1375 passed |
| Regulation domain | 17/17 |
| Regulation conversations | 17/17 |
| Regulation holdout | 25/25 |
| Example leakage | 0 |
| Unsupported concrete values | 0 |
| Ruff | passed |
| `git diff --check` | passed |

В полном `pytest` сохранилось одно известное предупреждение Starlette о
deprecated API; падений тестов не было.

Нулевые значения example leakage и unsupported concrete values означают, что
в зафиксированных наборах учебные примеры не использовались как данные
пользователя, а ответы не добавляли неподтверждённые конкретные значения.
Результаты относятся к указанным наборам и не означают 100-процентную точность
на любых будущих сообщениях.

## 4. Финальные production smoke-сценарии

### 4.1. Intake

| Сценарий | Ввод | Фактический результат |
|---|---|---|
| Мониторы | `нужно купить 7 мониторов для нового офиса` | Тип `goods`, категория G04 «IT-периферия», лишний вопрос «товар или услуга» не задавался; заявка полностью оформлена и зарегистрирована как `PR-2026-000035`. Номер подтверждает только этот конкретный smoke-сценарий. |
| Роутеры | `нужны 2 роутера для склада` | Тип `goods`; LLM предложила G03; пользовательское подтверждение потребовалось; после него диалог продолжился штатно. |
| Промышленный вентилятор | `нужно купить промышленный вентилятор для производственного цеха` | Тип `goods`; LLM предложила G15; пользовательское подтверждение потребовалось; после него диалог продолжился штатно. |
| Док-станция | `нужна док-станция для ноутбука` | LLM предложила G04; после подтверждения категория осталась G04, повторного вопроса о категории не было, бот перешёл к следующему незаполненному полю. |

Сценарий с док-станцией является финальной production-проверкой исправления
повторного использования подтверждённой категории: при неизменном semantic
context подтверждённое значение сохранилось, и повторного category
clarification не возникло.

### 4.2. Regulation Q&A

Production-проверка вопроса `Бумага А4 для печати` дала категорию G01
«Офисные принадлежности» со ссылкой на документ «Классификатор категорий
закупок».

Дополнительно локальным real-provider/regression тестированием подтверждены:

- сетевое оборудование → G03;
- самостоятельное инженерное оборудование → G15.

Последние два результата не обозначаются как повторно проверенные в production
после финального deployment: уровень доказательства для них — локальная
real-provider и regression-проверка.

## 5. Подтверждённый функциональный объём

### 5.1. Intake и lifecycle

Подтверждены:

- извлечение и уточнение обязательных полей товара и услуги;
- один сохраняемый черновик с восстановлением после навигации и reload;
- нормализация суммы, количества, единицы, даты и бюджетного статуса;
- безопасное определение типа закупки и категории;
- явное пользовательское подтверждение LLM-категории;
- блокировка unconfirmed, weak и stale category provenance до readiness и
  повторно при lifecycle confirm;
- карточка заявки и регистрация только после отдельного подтверждения;
- уникальный номер и пользовательский статус «Передана в отдел закупок»;
- отмена черновика и read-only история последних заявок владельца;
- типизированное разделение явной потребности «товар + услуга» до scalar draft.

### 5.2. Regulation Q&A

Подтверждены:

- отдельный режим с изоляцией от intake draft;
- understanding → slots → clarification → retrieval → grounded answer;
- persistent multi-turn clarification без хранения prompt, raw chunks или
  model payload;
- hybrid semantic + lexical retrieval и RRF;
- ответы только по нормативно допустимым источникам;
- проверка claims, конкретных значений и соответствия primary intent;
- отказ до retrieval для очевидных outside-domain вопросов;
- controlled refusal для актуальных цен и рекомендаций поставщиков;
- запрет переноса значений из examples/templates в данные пользователя.

## 7. Известные ограничения MVP

### 7.1. Natural selection в mixed procurement

После decomposition выбор отдельной позиции ограниченно понимает сокращённые
или изменённые естественные формулировки. Это известное P2-ограничение; обе
заявки автоматически не создаются.

### 7.2. Unit lexicon

Реестр единиц намеренно закрыт. Некоторые формы, например `пар/пары`, могут
потребовать явного выбора поддерживаемой нормализованной единицы. Это P2, а не
основание для небезопасного inferred `шт.`.

### 7.3. Формулировки service-уточнений

Некоторые разные поля услуги имеют похожие пользовательские формулировки
вопросов. Это UX/P2-ограничение; подтверждённой потери persistence нет.

### 7.4. Границы taxonomy

Используется синтетическая taxonomy учебного MVP. Пограничные
специализированные предметы могут потребовать уточнения или пользовательского
подтверждения. Это безопасное ограничение, а не ошибка классификатора.

### 7.5. Зависимость от LLM provider

Для предметов вне deterministic vocabulary предложение категории зависит от
OpenAI provider. При timeout, сетевой ошибке или невалидном результате система
оставляет категорию unresolved и не делает заявку готовой автоматически.

### 7.6. LLM latency

Real category-provider smoke показывал задержки порядка нескольких секунд.
Репрезентативная статистика и фиксированный SLA для MVP не заявляются.

### 7.7. Graceful shutdown

В отдельных предыдущих deployment после остановки aiogram polling Python
process не завершался до `TimeoutStopSec=30`, после чего systemd отправлял
SIGKILL. Последующие stop operations проходили штатно, поэтому ограничение не
считается постоянно воспроизводимым, но кодового исправления shutdown behavior
не зафиксировано.

### 7.8. Общие границы MVP

- одна заявка содержит один основной предмет, а не построчную спецификацию;
- история ограничена последними пятью read-only записями;
- нет кабинета закупщика, фактического согласования и внешних корпоративных
  интеграций;
- pending Regulation context обновляется неатомарно;
- длительное многопользовательское, нагрузочное и security-тестирование не
  проводилось;
- перед реальным пилотом нужны RLS, политика хранения, ротация секретов и
  отдельный security review.

Уже исправленные unsafe fallback G01–G04, regression типа для
router/monitor, taxonomy gap промышленного вентилятора, повторная
переклассификация подтверждённой G04, отсутствующий category RAG intent,
состояние индекса 117/118 и UUID relocation defect не относятся к текущим
ограничениям.

| Явное подтверждение перед регистрацией | Пройдено |

| Уникальный номер и статус после регистрации | Пройдено |
| История заявок владельца | Пройдена в пределах последних пяти записей |
| Regulation Q&A с источниками и clarification | Пройдено на зафиксированных наборах и production smoke |
| Example leakage / unsupported concrete values | 0 / 0 на финальных наборах |
| Промышленная эксплуатационная готовность | Не заявляется |

## 9. Итоговое решение

> **MVP принят по результатам финального функционального и production smoke testing с известными ограничениями.**

MVP соответствует функциональному объёму выпускного проекта. Основные сценарии
intake и Regulation Q&A реализованы; критические дефекты, выявленные rehearsal,
устранены и защищены regression-тестами. Production deployment, синхронизация
индекса и финальная smoke-проверка завершены.

Оставшиеся ограничения относятся к P2, UX и эксплуатационному scope и не
блокируют демонстрацию или защиту. При этом продукт не заявляется как готовая
enterprise production system: для реального пилота необходимы дополнительная
безопасность, эксплуатационные проверки и наблюдение на обезличенных реальных
формулировках пользователей.

# Telegram adapter MVP

## Статус

Telegram adapter MVP поддерживает пользовательский intake-сценарий от первого
описания потребности до регистрации или отмены черновика. Маршрут остаётся
тонким: Telegram → extraction → backend validators/intake core →
persistence orchestration → request lifecycle. Telegram-слой не содержит
собственных правил полноты, согласования, persistence или lifecycle.

## Реализовано

- отдельный aiogram 3 long-polling entrypoint;
- команда `/start` без создания пустого draft;
- поиск или создание внутреннего пользователя по числовому `users.telegram_id`;
- восстановление active draft и текущего вопроса;
- частичный разбор первого свободного сообщения: предмет, пользовательский тип,
  количество, единица, категория и, при явном формате, сумма, дата и место;
- только два пользовательских типа: «Товар» и «Услуга»;
- контекстные вопросы для товара и услуги;
- русские подписи технических enum-значений;
- автоматическая подстановка `contact_person` и `department` из профиля с
  `source=system`, без перезаписи введённых пользователем значений;
- отдельный deterministic category classifier с состояниями exact, multiple и
  no match;
- короткий список из 2–4 категорий при неоднозначности вместо полного реестра;
- временный deterministic parser;
- режимы extraction `rule`, `openai`, `hybrid` и тестовый `fake`;
- переиспользование общего OpenAI Responses provider и strict DTO без второго
  клиента в Telegram-слое;
- прямой вызов `PersistentIntakeOrchestrator`, без HTTP к FastAPI;
- детерминированный idempotency key `telegram:{chat_id}:{message_id}`;
- plain-text форматирование следующего вопроса и вариантов;
- постоянное главное меню: «Новая заявка», «Текущая заявка», «Мои заявки»,
  «Инструкция» и «Спросить по регламенту»;
- объединённая краткая инструкция с примерами товара и услуги;
- read-only список последних пяти завершённых lifecycle-заявок владельца;
- отдельный persistent-режим `regulation_qa`, использующий существующий hybrid
  retrieval и grounded answer service;
- пользовательская карточка на основе backend `RequestCard`;
- inline-действия подтверждения, возврата к редактированию и отмены;
- отдельное уточнение `budget_status=unknown` без ложного маршрута согласования;
- повторно безопасные callback, ownership-check и optimistic locking;
- контролируемые сообщения при ошибках формата, concurrency и backend.

Существующая схема `users` уже содержит уникальный `telegram_id bigint`, поэтому
новая миграция для этого среза не требуется. `username` не используется как
identity и не имеет отдельного поля в текущей схеме. `first_name` и `last_name`
используются для заполнения `full_name`, который затем может стать
`contact_person`. `department` не придумывается и подставляется только при
наличии в профиле.

Новая миграция также не требуется для режимов диалога: существующий
`dialog_states.current_intent` хранит `idle`, `intake` или `regulation_qa`.
Отсутствующее или старое значение выводится как `intake` при наличии active
draft и как `idle` без него. Обновление режима не заменяет `active_request_id`
или `state_data`. Replay вопросов хранится в существующем `message_logs` без
полного вопроса и Telegram ID.

## Конфигурация и запуск

Добавьте локально, не коммитя реальное значение:

```dotenv
TELEGRAM_BOT_TOKEN=your-bot-token
# Необязательное переопределение: rule, openai или hybrid
TELEGRAM_EXTRACTION_MODE=
TELEGRAM_EXTRACTION_DEBUG=false
APP_TIMEZONE=Europe/Moscow
RAG_ANSWER_MODEL=gpt-5.6-luna
RAG_ANSWER_TIMEOUT_SECONDS=30
```

`TELEGRAM_EXTRACTION_DEBUG=true` включает безопасную диагностику этапов
извлечения и количества ответов. Для корреляции используется короткий
fingerprint сообщения вместо Telegram `chat_id` и `message_id`. В диагностике
нет полного текста сообщения, токенов, ключей, prompt или персональных данных;
по умолчанию режим выключен.

Production entry point использует единственную цепочку: `handle_text_message` →
`TelegramIntakeAdapter.handle_text` →
`TelegramIntakeExtractionService.resolve_message` → intake merge → persistence →
completeness/next question → formatter. Evaluation вызывает тот же
`resolve_message`; production-wiring тесты дополнительно проверяют состояние
после повторной загрузки из persistence.

При hybrid merge точные локальные значения суммы, количества, единицы и срока
не заменяются менее точным structured-кандидатом. Для места выбирается более
полный подтверждённый вариант, если один вариант является частью другого. Для
услуги числовой объём остаётся в `specifications`, даже если structured extractor
вернул только текстовые требования. Повторная доставка того же Telegram
`message_id` не выполняет mutation и не отправляет второй `next_question`.

Явный deterministic сигнал `goods`/`service` также сохраняется при structured
`null`, отклонённом поле или provider fallback, но только вместе с evidence из
исходной фразы. Совпадающий structured type не меняет результат. Противоположный
тип не перезаписывает значение молча: оба кандидата удаляются из update, и
обычный intake flow запрашивает контролируемое уточнение типа закупки.

Бюджетный статус определяется детерминированно с приоритетом неопределённости,
затем явного отрицания и только затем положительного признака. Поэтому
`не знаю, забюджетировано ли` не становится бюджетной закупкой, а
`не забюджетировано` не совпадает с положительной формой. Поддерживаются, в
частности, `забюджетировано`, `заложено в бюджете`, `учтено в бюджете` и
`из утверждённого бюджета`.

Для карточки услуги общий `RequestCardBuilder` собирает читаемые требования из
описания, подтверждённых условий и числового объёма. Дубли удаляются, короткий
объём присоединяется к основному требованию, а неполный structured-result не
переносится в требования. `desired_result` остаётся отдельным полем и не
создаётся постобработкой.

Также необходимы серверные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`.
Запуск:

```powershell
python -m app.bot
```

Если режим не задан, при настроенном `OPENAI_API_KEY` выбирается `hybrid`, а без
ключа — безопасный `rule`. Явный `TELEGRAM_EXTRACTION_MODE` имеет приоритет. При
старте логируется только имя режима. При
отсутствии токена или Supabase-конфигурации entrypoint завершается с понятной
ошибкой. Импорт модулей и unit-тесты не создают Bot, Supabase или OpenAI clients.

## OpenAI-first hybrid extraction

Одно содержательное сообщение сначала разбирается локально, затем не более
одного раза передаётся общему `OpenAIApprovalExtractionProvider`. В запросе есть
только текущее сообщение, компактные подтверждённые поля draft, текущий вопрос
и ожидаемое поле; UUID, токены, ключи, lifecycle snapshot и история сообщений
не передаются. DTO предлагает кандидаты, после чего существующие validators и
intake core остаются источником истины.

Deterministic-слой authoritative только для однозначных суммы,
модификатора/периода суммы, абсолютной или относительной даты, явных
количества/единицы и бюджетного ответа. OpenAI authoritative для смыслового
типа, предмета, характеристик/объёма услуги, ожидаемого результата, категории,
места и обоснования. Поэтому локальный словарь не может заменить валидные
`service/Sxx` на `goods/Gxx` из-за товарного существительного внутри услуги.
Несовместимая пара `goods + Sxx` или `service + Gxx` не сохраняется, а категория
без подтверждённого типа или с низкой уверенностью остаётся пустой.
Если OpenAI оставил категорию пустой, допускается узкий fallback: локальный
классификатор повторно запускается после подтверждения `procurement_type` и
заполняет только единственный совместимый код нужного префикса. Он не
перезаписывает категорию OpenAI и не работает при неоднозначном или пустом типе.

Evidence для суммы, даты, количества, единицы, бюджетного статуса и места
должен быть прямым фрагментом сообщения. Для смысловых полей допускается
нормализованный исходный span: регистр, `ё/е`, пунктуация, кавычки и безопасные
русские падежные формы нормализуются без произвольного fuzzy matching.
Категория является derived field: evidence содержит исходный предмет или
действие, а validator отдельно проверяет существование кода G01–G15/S01–S15 и
его совместимость с типом. Неподтверждённое смысловое поле отклоняется отдельно,
не ослабляя проверку прямых фактов.

Timeout, rate limit, ошибка сети или невалидный structured output безопасно
переводят сообщение на консервативный deterministic fallback. Он сохраняет
только сумму с модификатором/периодом, дату, явные количество/единицу и
бюджетный статус; тип, категорию, предмет, требования и результат не угадывает.
Completeness-механизм задаёт следующий уточняющий вопрос. В журнал попадают
режим, класс
ошибки и счётчики предложенных/принятых полей, но не полный текст заявки,
structured output, prompt или секреты. Пользователю не показываются сведения об
OpenAI. Меню, `/start`, помощь, примеры, показ карточки и lifecycle callback не
вызывают extractor; простой ответ на вопрос о бюджете также остаётся локальным.
Fallback оформлен методом application service `resolve_message`: его вызывает и
рабочий adapter, и hybrid evaluator. Поэтому evaluation не содержит отдельной
копии правил деградации.

Явные исправления (`не X, а Y`) представлены общей metadata
`operation=replace`, `target_field`, `old_value`, `new_value`. Новое значение
имеет приоритет над текущим draft и предыдущим extraction candidate; старое
значение не сохраняется как итог.

Для услуг structured `item_name` проходит узкую UX-нормализацию: дубли вроде
«установка — установить кондиционер» преобразуются в «установка
кондиционера». Нормализация применяется только когда существительное действия
и следующий инфинитив обозначают одно действие; обычные названия с тире не
переписываются. G09 в компактном справочнике включает общий класс моющих и
чистящих средств, губок, салфеток и хозяйственного инвентаря. Тип закупки
остаётся обязательной границей: товары для уборки относятся к G09, услуга
уборки — к S02.

Значения из первичного structured/deterministic extraction являются
предварительными (`source=extraction`, `confirmed=false`). Контекст текущего
вопроса имеет приоритет: содержательный ответ пользователя сохраняется как
`source=user`, заменяет такое предложение без confirmation flow и переводит
диалог к следующему незаполненному полю. Явная конструкция исправления другого
поля (`не X, а Y`) по-прежнему обрабатывается как коррекция. Для текстовых
требований новый независимый факт обогащает `specifications` или
`desired_result`, а не уничтожает уже собранные сведения.

Инфинитивный результат, который лишь повторяет предмет услуги, отбрасывается до
проверки полноты: `установка кондиционеров` + `установить кондиционеры` оставляет
`desired_result` пустым. Осмысленный эффект, например работа кондиционеров по
заявленным характеристикам, сохраняется как результат, а условие проведения
работ утром — как `specifications`.

Настоящий конфликт создаётся только при попытке заменить ранее подтверждённое
пользовательское значение. Пока конфликт активен, обычный parser и extractor не
запускаются: `подтвердить`, `да`, `изменить`, `применить` выбирают новое
значение; `оставить`, `не менять`, `нет` сохраняют прежнее. Неизвестный ответ
возвращает короткую подсказку, не создавая второго conflict. Повтор сообщения с
тем же Telegram `message_id` возвращает закэшированный исход, а повторное
разрешение уже удалённого conflict безопасно ничего не меняет.

## Поведение

`/start` разрешает внутреннего пользователя, сбрасывает conversational mode в
`idle`, очищает только regulation pending, читает active session и показывает
согласованное короткое приветствие и постоянное меню. Команда сама не создаёт
draft. При наличии активного черновика бот сообщает, что его можно продолжить
через «Текущую заявку» или явно отменить перед началом новой; существующие данные
не сбрасываются.

Сообщения главного меню и navigation callbacks маршрутизируются до intake
parser. «Новая заявка» без
active draft только переводит UI в ожидание содержательного описания; сам draft
создаётся первым intake step. При active draft предлагаются продолжение,
возврат в меню или отмена с дополнительным подтверждением. «Текущая заявка»
показывает краткое состояние и следующий вопрос либо полную карточку.
«Инструкция» объединяет правила работы и два примера и является read-only.

Режимы `idle`, `intake` и `regulation_qa` сохраняются в
`dialog_states.current_intent`. В `regulation_qa` обычный текст не проходит
через intake parser и не изменяет активный draft; переход в другой раздел меню
явно завершает режим. После рестарта режим восстанавливается из persistence.
Повторно доставленный вопрос возвращает сохранённый результат и не вызывает
retrieval и answer provider второй раз.

Каждое нажатие «Спросить по регламенту» является явным clean re-entry:
предыдущее multi-turn уточнение удаляется, даже если режим уже был
`regulation_qa`. Активный draft остаётся доступным и не изменяется. Переход в
«Новую заявку» очищает regulation pending и включает intake mode.

В режиме вопросов показывается одна навигационная кнопка «⬅️ Главное меню».
Старый callback `regulations_end` остаётся совместимым и также возвращает в
`idle`, но новым сообщениям больше не выдаётся.

«Мои заявки» читает последние пять зарегистрированных или отменённых заявок
только текущего внутреннего пользователя; черновики туда не входят. Карточка
строится общим `RequestCardBuilder`, а для зарегистрированной заявки предпочитает
неизменяемый `lifecycle.final_request_card`. История не предоставляет mutation:
зарегистрированные карточки через Telegram не редактируются.

«Спросить по регламенту» вызывает существующий `KnowledgeRetrievalService`, а
затем отдельный grounded answer provider. В ответе отображаются дедуплицированные
названия документов, но не UUID, chunk ID, similarity и prompt. Пустой вопрос,
слишком длинный вопрос, отсутствие релевантных chunks и техническая ошибка
обрабатываются контролируемо. Подробный контракт описан в
[`regulation_qa.md`](regulation_qa.md).

Реальный end-to-end smoke test подтвердил одинаковое решение для сумм с
разными разделителями тысяч и для сроков «10 дней», «14 дней» и «две недели».
Проверка ответа сверяет конкретные суммы и сроки с нормативными источниками;
частные значения из учебных примеров не переносятся в ответ как данные
пользователя. Вопросы о текущих ценах поставщиков отклоняются контролируемо,
поскольку таких данных в базе знаний нет.

## Карточка и lifecycle-действия

Карточка строится из результата backend `RequestCard`, а не из отдельной
Telegram-копии бизнес-правил. Для товара выводятся товарные поля, для услуги —
описание и ожидаемый результат; пустые необязательные строки скрываются.
Технические enum, UUID, version и evidence пользователю не показываются. Сумма
форматируется в рублях; `maximum` отображается как «не более», `approximate` —
как «около».

Для готовой заявки доступны «Подтвердить и отправить», «Изменить» и «Отменить».
Confirm вызывает backend lifecycle с владельцем, ожидаемой версией и
идемпотентным callback key; успешный ответ содержит номер заявки. Повтор того же
callback не создаёт вторую регистрацию. Return-to-edit переводит draft через
lifecycle в editing, после чего обычное сообщение применяется как явное
исправление. Отмена требует второго нажатия и вызывает lifecycle cancel без
физического удаления записи.

Если бюджетный статус равен `unknown`, карточка показывается, но кнопки confirm
нет. Пользователь может вернуться к вопросу о бюджете, выбрать «предусмотрена»,
«не предусмотрена» или оставить «не знаю»; выбор сохраняется обычным intake
update, а возможность регистрации снова определяет backend.

Callback data содержит компактные action, request ID и expected version и
укладывается в лимит Telegram 64 байта. Lifecycle проверяет ownership и state.
При stale version adapter перечитывает активную заявку и показывает актуальные
действия; данные чужой заявки не раскрываются. Callback query получает answer
даже при контролируемой ошибке, а `TelegramBadRequest` при работе со старым
сообщением не приводит к повторной mutation.

После регистрации либо отмены с выбором новой заявки прежний draft больше не
active, а adapter переходит в `awaiting_new_request_description`. Длинное
приглашение отправляется ровно один раз и inline-клавиатура старого сообщения
снимается. Повторный callback или пункт меню отвечает коротко и не создаёт
draft; независимый draft создаётся только следующим содержательным сообщением.
Из старой заявки не копируются бизнес-поля, системное заполнение профиля
(`contact_person`, `department`) сохраняется.

«Текущая заявка» показывает только active draft; завершённые lifecycle-заявки
доступны отдельно через «Мои заявки» и остаются read-only.

В `rule` первое обычное сообщение разбирается контролируемыми regex и небольшими
словарями. В `hybrid` смысловые кандидаты дополняются structured extractor, но
все найденные поля по-прежнему передаются ядру одним update: следующий вопрос
выбирает backend и уже названные значения повторно не запрашиваются.

Фраза про услуги по сборке трёх шкафов и двух столов классифицируется как
`service`, S15. Объекты сохраняются как объём в `specifications`, а не как
товарные `quantity=5`/`unit=шт.`. Выражение «на 6 августа» выделяется моделью в
исходной форме и повторно нормализуется `NaturalDateParser`.

На пользовательском уровне `goods` показывается как «Товар», а `service` — как
«Услуга». Ремонт, монтаж и другие работы классифицируются как услуги. Новый
Telegram input не принимает устаревшее техническое значение `work`.

Category classifier использует фактический реестр категорий и небольшой набор
ключевых слов. Точное совпадение записывается автоматически. При нескольких
вариантах adapter каждый раз детерминированно пересчитывает кандидатов из
канонических `procurement_type`, `item_name` и `description` draft. Поэтому
выбор по номеру переживает рестарт процесса без Redis, новой таблицы или
ненадёжного in-memory состояния. При отсутствии совпадения задаётся смысловой
уточняющий вопрос без показа всех 30 категорий.

Ответ на дату поддерживает `YYYY-MM-DD`, `DD.MM.YYYY`, «20 августа», «к 20
августа», «до 20 августа», «завтра», «послезавтра», а также цифровые и
словесные конструкции «через N дней/недель/месяцев» и «через квартал».
Дни и недели считаются календарными днями, месяц и квартал — календарным
смещением с корректной обработкой конца месяца. Расчёт идёт от локальной даты
`APP_TIMEZONE`. Если год не указан, выбирается ближайшая будущая дата.

Сумма поддерживает целое число, разделённые обычными или неразрывными пробелами
разряды, `руб.`, `₽`, `тыс.` и «тысяч», а также «не более», «до», «максимум»,
«около», «примерно», «ориентировочно» и «порядка». Initial span extraction,
короткий ответ на вопрос суммы и structured normalization используют одну
грамматику modifier/value/currency/period. Финальные `.`, `,`, `!` и `?` не
меняют семантику суммы. Число сохраняется в `amount`, а semantic modifier
`exact`, `maximum` или `approximate` — в evidence состояния поля. Диапазон
суммы не помещается в scalar intake-поле и контролируемо требует уточнения как
в initial, так и в clarification path.

Все пути unit normalization используют один canonical alias registry. Единицы
`шт`, `штука`, `штуки`, `штук` и `единиц` нормализуются в `шт.`; формы
`пачка`, `пачки`, `пачек` — в `пач.`; формы упаковок, коробок и комплектов — в
соответствующие канонические значения. Явная физическая или упаковочная единица
имеет приоритет над inferred `шт.` и сохраняется в canonical draft до
persistence reload.

Количество распознаёт цифры и безопасный набор русских количественных
числительных от одного до ста, включая падежные формы и составные десятки.
Порядковые числительные не принимаются. Для товара конструкция «число +
предметное существительное» получает `unit=шт.` только при отсутствии явной
единицы. Реестр мер и упаковки имеет приоритет: литры, килограммы, метры,
пачки, упаковки, коробки и комплекты сохраняют собственную каноническую единицу.
Конструкции «объёмом N» и «по N литров» сохраняются в `specifications` как
характеристика одной позиции и не перемножаются с quantity. Два независимых
товарных количества (`3 шкафа и 2 стола`) не сводятся в одну строку quantity;
детерминированный veto также удаляет возможный агрегированный quantity
structured provider. Для услуги такие числа остаются объёмом в требованиях.

В свободном первом сообщении сумма извлекается единым ограниченным span: вместе
с формулировкой «бюджет»/«ориентировочная сумма», модификатором, числом,
масштабом и валютой. Это предотвращает частичные остатки вроде «лей». После
удаления span нормализуются пробелы и пунктуация. Явные периоды «в/за месяц»,
«в квартал», «в/за год», «ежемесячно» и «ежегодно» сохраняются рядом с
`amount_modifier` в `field_states.amount.evidence` как `billing_period`. В
карточке показываются только русские суффиксы: «в месяц», «в квартал», «в год».

Абсолютная и относительная дата ищется не только в коротком ответе, но и внутри безопасных
оболочек: «с 1 сентября», «начиная с 1 сентября», «дата — 1 сентября»,
«как я уже написала, с 1 сентября». Для услуги она сохраняется в существующем
`desired_delivery_date` и отображается как «Срок оказания услуги». Маркер
`через` означает deadline; `в месяц` после суммы остаётся billing period,
`раз в неделю` — frequency, а `в течение недели` — duration. Неоднозначные
«скоро», «через пару недель» и «к концу месяца» по-прежнему требуют уточнения.

Для нескольких типовых услуг parser отделяет краткий предмет от ограниченного
набора деталей: площадь и очевидное место выполнения. Сумма, дата, валюта и
период оплаты в `item_name` не попадают. Formatter сравнивает нормализованные
`item_name`, `description`, `specifications` и `desired_result`, удаляя полные
повторы, но сохраняя дополнительные требования. В Telegram-карточке
`specifications`/описание выводятся как «Объём и требования», а
`desired_result` — отдельной строкой «Ожидаемый результат». Сегменты
user-confirmed имеют приоритет, extraction добавляет только отсутствующие
детали. Это консервативные правила, а не поддержка произвольного русского языка.

Для суммы состояние unknown пока отсутствует: нужна хотя бы ориентировочная
оценка. Для `budget_status` поддержано каноническое `unknown`. Ответ «Не знаю»
считается заполненным и не зацикливает вопрос. Автоматический маршрут при этом
не выбирается: карточка помечает бюджет как требующий уточнения, а действующая
lifecycle policy блокирует confirm до проверки бюджетного статуса.

Повторно доставленное Telegram-сообщение получает тот же idempotency key.
Adapter кэширует итог одного обработанного `message_id`, поэтому replay не
запускает extractor повторно и не пересобирает update относительно уже
изменившегося next question. Persistence idempotency остаётся второй защитой.

## Примеры диалога

### Офисные кресла

Пользователь: «Нужно купить 10 офисных кресел».

Adapter извлекает товар, предмет, количество, `шт.` и G02. Backend сразу задаёт
первый действительно незаполненный вопрос, например о характеристиках товара.

### Уборка офиса

Пользователь: «Нужно заказать уборку офиса 3 раза в неделю».

Adapter определяет услугу и S02, сохраняет частоту в описании, но не выдаёт её
за количество. Следующие вопросы формулируются в терминах услуги и результата.

### Неоднозначная категория

Пользователь: «Нужно компьютерное оборудование».

Бот предлагает только два варианта — «IT-оборудование» и «IT-периферия» — и
принимает номер или название. Полный реестр пользователю не показывается.

Варианты категории сохраняются в `dialog_states.state_data` вместе с кодами,
пользовательскими названиями, provenance, признаками `selectable` и
`readiness_eligible`, а также идентификатором шага. Поэтому после перезапуска
adapter принимает номер только из ранее показанного strong-списка. Запросы «какие
варианты?» и «дай список категорий» повторяют сохранённый список. Если ответ не
распознан и вопрос начинает повторяться, бот показывает варианты и предлагает
вернуться к описанию предмета вместо бесконечного цикла.

Если classifier не получил positive support, прежний общий fallback
G01–G04/Sxx не показывается как набор подходящих вариантов. Бот сообщает, что
категорию не удалось определить уверенно, и просит уточнить назначение или
описание. Legacy-кандидаты без provenance при восстановлении считаются weak и
не становятся основанием readiness.

После deterministic `none` adapter может вызвать closed-taxonomy category
provider. Это не повторный общий extraction и не RAG: provider получает только
категории текущего типа из канонического registry, а strict DTO возвращает
`exact`, 2–3 `candidates` или `unresolved`. При deterministic exact provider не
вызывается. Конструкции, где известное слово является лишь объектом отношения
(`подставка под монитор`), не считаются strong exact только по вложенному слову.

`llm_exact` показывается как предположение с вариантами «Да» и «Выбрать другую»;
`llm_candidates` показывает только 2–3 проверенных варианта. До явного ответа
category остаётся `null`. После номера, полного/частичного названия или
подтверждения сохраняется `category_support=llm_confirmed:<fingerprint>:<code>`.
Список переживает reload adapter, но не переиспользуется после изменения предмета
или procurement type. Provider failure даёт controlled clarification без общего
списка и не блокирует deterministic happy path.

Category evidence допускает безопасные изменения русских окончаний: например,
`настенная панель` подтверждает `настенную панель`. При этом все содержательные
токены evidence должны совпасть непрерывно и в том же порядке; одного общего
слова или семантически другого предмета недостаточно.

Один и тот же механизм используется для товаров и услуг. Для программного
обеспечения он следует существующему классификатору: готовая лицензия,
подписка и SaaS относятся к G05 «ПО и лицензии»; установка и настройка
уже лицензированного ПО, разработка, доработка и интеграция — к S05
«IT-разработка и поддержка». Сочетание глагола «установить» с упоминанием
лицензии без указания, что лицензии уже приобретены, не выбирает S05:
adapter сохраняет черновик и уточняет, требуется ли также закупка лицензий.
Если нужны и лицензии, и установка, правило о разных категориях требует двух
заявок G05/S05. Общее «ПО для сотрудников» без указания результата также
оставляет кандидаты G05/S05. Номер, полное и частичное название сверяются
только с сохранёнными кандидатами.

Текущая модель черновика не содержит отдельного поля для даты возможного
начала работ. Такая дата сохраняется в исходном описании услуги, а поле
`required_date` используется только для конечного срока исполнения.

### Товары разных категорий

До проверки полноты deterministic parser выделяет известные товарные позиции.
Если позиции относятся к разным категориям, единый черновик блокируется, а в
`state_data` сохраняются только типизированные кандидаты: предмет, тип,
предполагаемая категория и количество. Срок и место, уже извлечённые из
исходного сообщения, остаются в черновике. После выбора одной позиции в
актуальную заявку переносятся только выбранный предмет и его категория;
остальные позиции не становятся частью заявки автоматически. Несколько
позиций одной категории могут оставаться в одном описании.

### Составная потребность «товар + услуга»

До обычного scalar intake adapter выполняет типизированную decomposition.
Высокоточные признаки строятся по паре действий: самостоятельное приобретение
товара и отдельно заказанное действие установки, монтажа, укладки, сборки или
обслуживания. Определение не зависит от закрытого списка названий товаров.

Результат содержит вид (`single_need`, `multiple_goods`,
`goods_plus_service` или `ambiguous`), типизированные потребности, evidence,
возможные категории, общий контекст и fingerprint. При `goods_plus_service`
scalar-поля предмета и категории не записываются до выбора пользователя, а бот
объясняет необходимость отдельных заявок. Срок и явно общий адрес сохраняются;
количество товара не переносится в услугу.

Доставка товара поставщиком как условие товарной закупки не считается отдельной
услугой. Сборка нескольких предметов, ремонт, перевозка и уборка без отдельного
глагола приобретения остаются одной услугой. Неявные или недостаточно уверенные
составные формулировки не разделяются автоматически.

Category candidates сохраняются вместе с актуальным `procurement_type` и
fingerprint decomposition. После смены типа кандидаты с противоположным G/S
префиксом отбрасываются, включая восстановление после reload. Выбор номером,
кодом или названием работает только внутри актуального набора.

Перед readiness и повторно при lifecycle confirm выполняется semantic category
guard. Для заполненной категории требуется positive support: exact classifier,
strong multiple/derived candidate либо подтверждённый пользовательский выбор из
такого списка. Существования кода, G/S-префикса или membership в weak fallback
недостаточно. Если classifier возвращает `none` и strong provenance нет, поле
остаётся invalid и карточку нельзя подтвердить. Lifecycle повторяет эту
проверку перед регистрацией. Неоднозначные соседние категории, например
IT-оборудование и периферия, сохраняют явно разрешённый контракт.

### Совместимость короткого ответа с ожидаемым полем

Для readiness-critical free-text уточнений действует ограниченный
deterministic guard. `department` не принимает очевидное описание цели, места
или даты; contact person не принимает такие же явно чужие конструкции;
delivery location не принимает очевидную дату или цель. При mismatch значение
не переносится автоматически в другое поле, не отправляется structured
extractor и не сохраняется. Пользователь получает понятную подсказку и повторно
отвечает на тот же вопрос. Нормальные ответы профиля, названия подразделений,
имена и адреса продолжают использовать существующий путь.

## Production update после ручного smoke test

Новая миграция и переиндексация knowledge base для этого milestone не нужны.
После ручного подтверждения в тестовом Telegram-чате нужно обновить код обычным
deployment-процессом проекта, проверить наличие `RAG_ANSWER_MODEL` и
`RAG_ANSWER_TIMEOUT_SECONDS` в окружении (либо оставить документированные
defaults), выполнить проверки выше и перезапустить `purchasing-ai-bot.service`.
После рестарта следует проверить пять пунктов меню, ownership в «Моих заявках»,
восстановление активного черновика и один grounded-ответ с источником. Логи
проверяются только по безопасным fingerprint и счётчикам; полный вопрос и
контекст документов там появляться не должны.

## Пока не реализовано

- качество `openai`/`hybrid` подтверждено на зафиксированных наборах и ручных
  сценариях, но это не доказывает универсальную точность на новых сообщениях;
- `rule` по-прежнему намеренно ограничен и служит fallback, а не универсальным
  пониманием русского текста;
- decomposition уверенно покрывает явные конструкции «приобрести X и отдельно
  выполнить действие с X», но не является полноценной многопозиционной моделью;
- после выбора первой потребности вторая не создаётся автоматически: новую
  заявку пользователь начинает отдельно;
- выражения «скоро», «через пару недель», «к концу месяца» и подобные намеренно
  требуют уточнения;
- выбор отдельного поля кнопкой «Изменить» (MVP принимает свободное текстовое
  исправление после lifecycle return-to-edit);
- semantic correctness grounded-ответов требует отдельной ручной или
  разрешённой model-based оценки; offline proxy проверяет retrieval и контракт,
  но не доказывает смысловую правильность ответа;
- история ограничена пятью read-only карточками текущего пользователя и не
  является интерфейсом закупщика;
- файлы и голосовые сообщения;
- webhook не используется; production-развёртывание работает через long
  polling и `purchasing-ai-bot.service`;
- интерфейс закупщика и исполнение согласований.
Category resolution строит единый semantic context из канонического draft:
`procurement_type`, `item_name`, описания, требований, ожидаемого результата и
бизнес-цели. Текущая реплика добавляется только когда несёт новый предметный
смысл. Сумма, бюджет, дата, подразделение, контакт и другие несвязанные поля в
контекст категории не входят.

Отдельный `category_context_fingerprint` защищает от повторных LLM-вызовов без
новой информации. Обогащение назначения или требований меняет fingerprint и
разрешает повторную классификацию после `unresolved`; ответы про сумму, бюджет
или срок повторный вызов не запускают. Состояние хранится в существующем JSON
`dialog_states.state_data`, поэтому миграция базы данных не требуется.

В production logs фиксируются только безопасные диагностические признаки:
тип закупки, fingerprint, версия taxonomy, deterministic/provider decisions,
reason code, коды кандидатов и длительность. Исходный пользовательский текст,
prompt, credentials и model payload не журналируются.

Closed taxonomy использует версию `intake-categories-v3`. Сетевые и другие
инфраструктурные IT-устройства относятся к G03, периферия рабочего места — к
G04. Самостоятельное инженерное/промышленное оборудование и его запчасти
относятся к G15. LLM классифицирует эти классы по semantic metadata; отдельные
noun mappings для роутеров, вентиляторов, насосов и аналогичных предметов не
добавляются.

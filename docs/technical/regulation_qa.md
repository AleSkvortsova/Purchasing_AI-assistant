# Grounded Q&A по регламентам

## Архитектура

Telegram Q&A не создаёт второй RAG. Цепочка использует существующие компоненты:

```text
Telegram regulation_qa
→ RegulationQuestionAnsweringService
→ RegulationQuestionUnderstanding
→ positive domain gate: known / ambiguous / outside
→ slot-based clarification / unsupported-capability routing
→ deterministic query plan (до пяти вариантов)
→ KnowledgeRetrievalService
→ OpenAIEmbeddingProvider
→ SupabaseKnowledgeRepository
→ match_knowledge_chunks_hybrid RPC
→ OpenAIGroundedAnswerProvider
→ ответ и уникальные источники
```

Настройки `RAG_TOP_K`, `RAG_SIMILARITY_THRESHOLD`, `RAG_RETRIEVAL_MODE`,
candidate counts, `RAG_RRF_K` и веса берутся из `Settings`. Handler не задаёт
собственных retrieval-порогов. Supabase RPC уже фильтрует только активные
knowledge documents. README и служебные файлы в индекс не входят.

Процесс не загружает embeddings или всю базу знаний в память: для каждого
варианта вопроса создаётся query embedding, а фрагменты возвращаются Supabase RPC. Один
Supabase client и один OpenAI client переиспользуются extraction, embedding и
answer providers, при этом prompt contracts остаются раздельными.

До retrieval детерминированный understanding layer создаёт закрытую Pydantic-
модель `RegulationQuestionUnderstanding`. Она хранит основной и дополнительные
intent, решение `known_domain_intent` / `ambiguous_domain` / `outside_domain`,
сумму, бюджетный статус, относительный срок, статус заявки, предмет, тип и
категорию закупки, известные и обязательные отсутствующие поля. Неизвестный
текст больше не превращается в `required_fields`: для запуска retrieval нужен
положительный закупочный сигнал. Очевидный outside-domain вопрос получает
контролируемый отказ до query expansion, embedding и retrieval.

Domain gate также учитывает назначение покупки, а не название предмета.
Явное личное назначение («себе», «домой», «для семьи») без организационных
признаков даёт `outside_domain` до retrieval; офис, подразделение, сотрудник,
склад или рабочее место подтверждают внутренний контекст. Если одновременно
присутствуют личное и рабочее назначения, система запрашивает уточнение.
Канонические вопросы о статусах, согласовании и срочности сами являются
достаточным нормативным intent и не требуют слова «офис».

Уточнение строится по отсутствующим слотам. Например, для маршрута согласования
обязательны сумма и бюджетный статус, а для общего вопроса «Что мне указать?» —
тип и краткое описание предмета. Supplier recommendation определяется как
outside-KB intent до retrieval: база и answer provider в этой ветке не
вызываются. Слишком широкий вопрос возвращает короткое меню доступных тем.
Обе ветки являются direct answers: `general_help` возвращает уточнение с меню,
а outside-KB — контролируемый отказ без запуска retrieval.

Query plan нормализует разделители тысяч и масштабы (`180 000`, `180.000`,
`180 тыс.`), русские числительные и эквивалентные формулировки бюджетного
статуса. Отрицание и неизвестный бюджетный статус сохраняются отдельно.
Точные фразы статусов не теряются. План хранит несколько intent для
многосоставного вопроса и добавляет ограниченную терминологию для согласования,
срочности, статусов, категориальных полей, перевозки и смешанных категорий.
Original, concise factual и terminology-expanded варианты каждый
проходят через существующий hybrid retrieval. Их позиции объединяются вторым
position-based RRF с тем же `RAG_RRF_K`; raw scores не складываются.

Слово «черновик» классифицируется по конструкции вопроса. Действия
сохранить/продолжить/вернуться дают `draft_and_history`; формулировки «что
означает статус» и «какие переходы из статуса» сохраняют
`status_explanation`. Вопрос о сохранении черновика проходит retrieval по FAQ
или пользовательской инструкции и не опирается только на справочник статусов.

Cancellation intent определяется общей парой action/target: отменить, снять,
удалить или отказаться — и заявка, черновик, запрос либо закупка. Расстояние
между словами не ограничено фиксированным числом символов. Название статуса
«Отменена» без действия остаётся вопросом о статусе.

Relevance filtering принимает нормативные документы, FAQ и инструкции, когда
каждый из них подтверждает отдельный аспект вопроса. Один фрагмент не обязан
покрывать весь многосоставный вопрос. Examples/templates по-прежнему не могут
служить нормативным доказательством.

Generated `search_vector` migration 003 уже включает `document_title`,
`section_path`, `heading` и `content`, поэтому изменение индекса или
переиндексация для этой доработки не нужны.

## Grounding

Structured DTO ответа содержит текст, проверяемые claims, флаг недостаточного
контекста и противоречие источников. Каждый claim содержит собственные
`cited_chunk_ids`, должен входить в итоговый answer и подтверждаться текстом
источника. Service принимает только реально переданные чанки, проверяет
релевантность claim обязательному primary intent исходного вопроса, конкретные
числовые значения и длинное дословное копирование. Secondary intent может
дополнить ответ, но не заменить primary intent. Сам факт наличия похожего
фрагмента не является доказательством релевантности ответа.

Тип документа переводится в `normative`, `instruction`, `faq`, `example` или
`template`. Для обычного вопроса examples/templates удаляются из контекста,
если найден подтверждающий нормативный или инструктивный чанк. Конкретное
значение, отсутствующее в вопросе, допустимо только если оно присутствует в
цитируемом не-example источнике. Поэтому частный пример перевозки из `kb-011`
не может превратить 12 паллет пользователя в 4 тонны, маршрут через Химки,
дату, гидроборт или бюджет примера.

Суммы, количества и относительные сроки приводятся к единому виду при подготовке вопроса и
проверке ответа. Пробел, NBSP, точка-разделитель тысяч и обозначение рублей не
меняют сумму. Числительные от единиц до десятков поддерживаются общим
детерминированным преобразованием: «четыре дня», «семь паллет» и «девяносто
пять тысяч рублей» становятся `4 дня`, `7 паллет` и `95000 рублей`.
«Две недели» считаются как 14 дней без вычисления календарной
даты. При выводе по порогу приложение, а не LLM, детерминированно проверяет
принадлежность суммы нормативному диапазону и сравнивает длительность с
процитированным нормативным сроком. Пользователь получает естественное
объяснение, например: «До мероприятия осталось две недели, то есть 14 дней.
Это меньше нормативного срока в 30 календарных дней…».

Онтология мероприятий объединяет конференции, форумы, семинары, выставки,
презентации, корпоративные события и явно внешние деловые встречи с нормативом
категории мероприятия. Обычный созвон, внутреннее совещание или обычная встреча
без закупочного контекста к этой категории автоматически не относятся.

Если маршрут согласования зависит от отсутствующего бюджетного статуса, service
возвращает `clarification_required` и типизированный `clarifying_question`, а
не общий отказ. Общие вопросы о срочности, статусах и обязательных полях не
требуют параметров конкретной заявки.

При отсутствии контекста service отказывается угадывать. Внутренние reason code
различают `no_chunks`, `no_relevant_normative_chunks`, `unsupported_answer`,
`ambiguous_question`, `provider_unavailable` и `malformed_output`. Diagnostic
script дополнительно показывает `below_threshold`. Ошибки retrieval, timeout
или malformed provider response дают безопасный статус. В логах
остаются только fingerprint сообщения, статус, числа чанков/источников,
duration и безопасный error code; вопрос, context, prompt и raw response не
логируются.

Некорректный structured answer не становится пользовательской ошибкой. Service
делает один controlled repair по безопасному коду причины, затем пытается
сформировать проверяемый deterministic answer из структурированных нормативных
данных. Если это невозможно, он возвращает slot clarification или
`insufficient_context`. Проверки идентификаторов фрагментов, релевантности,
конкретных значений и запрет examples/templates при этом не отключаются.

## Изоляция диалога

`dialog_states.current_intent` хранит `idle`, `intake` или `regulation_qa`.
Переход в Q&A не меняет `active_request_id` и canonical draft. В этом режиме
Telegram adapter возвращает управление до вызова deterministic parser,
structured intake extraction, completeness и lifecycle. В intake RAG не
вызывается.

Кнопка «Спросить по регламенту» всегда означает clean re-entry: устанавливает
`regulation_qa` и удаляет только старое regulation clarification. Активный
intake draft и его canonical data сохраняются. Переход к новой заявке включает
`intake` и также очищает regulation pending. Команда `/start` переводит диалог
в нейтральный `idle`, очищает pending, но не удаляет и не меняет активный draft;
при его наличии пользователь видит уведомление о сохранённой заявке.

Повторный Telegram message использует существующий idempotency namespace в
`message_logs`. Полный вопрос и открытые Telegram ID туда не записываются.

### Многошаговые уточнения

Если ответ имеет статус `clarification_required`, Telegram adapter сохраняет в
`dialog_states.state_data.regulation_pending_clarification` типизированный
контекст: исходный вопрос, primary/secondary intents, известные и отсутствующие
slots, текст уточнения, номер шага и время создания. Retrieved chunks, prompt,
request body и OpenAI payload в dialog state не сохраняются.

Следующее сообщение сначала интерпретируется как ответ на активное уточнение.
Новые slots объединяются с сохранёнными, после чего приложение либо задаёт
следующий вопрос, либо выполняет retrieval уже с полным структурированным
контекстом. Полный новый вопрос заменяет незавершённое уточнение. Контекст
очищается после ответа, перехода в главное меню или через 30 минут.

Pending хранится только во вложенном ключе
`dialog_states.state_data.regulation_pending_clarification`; остальные ключи
`state_data`, включая intake state, сохраняются последовательным
read-modify-write. Новая миграция для этого не требовалась: используются
существующие JSONB-поле `state_data` и `message_logs`.

Primary и secondary intents активного уточнения имеют приоритет над повторной
классификацией короткого ответа. Поэтому сообщение может заполнить сразу
несколько slots (например, сумму и бюджетный статус), не превращаясь в новый
вопрос об обязательных полях. Для защиты от циклов состояние хранит fingerprint
последнего вопроса и ограничивает диалог тремя шагами. Значение бюджетного
статуса `unknown` считается осознанным ответом: приложение не повторяет тот же
вопрос, а объясняет, что без подтверждённого статуса маршрут нельзя выбрать
однозначно.

Для маршрута согласования, срочности, отмены, статусов и обязательных полей
приложение сначала вычисляет решение детерминированно. RAG подтверждает правило
и предоставляет источник; answer model не пересчитывает маршрут из свободного
текста, если сумма и бюджетный статус уже известны.

## Evaluation

`data/evaluation/regulation_qa_cases.json` содержит regression-набор вопросов: прямые факты,
суммовые пороги, условный маршрут, обязательные поля, статусы, срочность,
смешанные категории, ответственность, неоднозначность и вопрос вне базы.

Наборы качества разделены: 20 production regression cases хранятся в
`regulation_qa_production_cases.json`, а первый независимый holdout из 25
вопросов — в `regulation_qa_holdout_cases.json`. Второй blind holdout хранится
отдельно и фиксируется до первого выполнения, чтобы результаты не использовались
для настройки кода.

Отдельный `regulation_domain_cases.json` содержит независимые бытовые OOD,
near-domain, ambiguous и конфликтные status/draft формулировки. Скрипт
`evaluate_regulation_domain.py` вызывает фактический offline service flow и
раздельно считает domain classification, OOD rejection, primary intent,
final-answer relevance, source support, unsupported concrete values и example
leakage.

Строгая end-to-end метрика разделена на две независимые части:

- `user_answer_success_rate` проверяет статус, ответ, источники, уточнение и
  отсутствие запрещённых тезисов;
- `understanding_structure_accuracy` проверяет primary intent, точный набор
  secondary intents и slots.

Дополнительно выводятся `primary_intent_accuracy`,
`secondary_intent_accuracy`, `slot_accuracy` и `safe_failure_rate`. Поэтому
правильный пользовательский ответ с пропущенным secondary intent учитывается
как успешный ответ, но как ошибка структуры understanding.

Оценка источников также разделена. `exact_source_match` показывает совпадение
с ожидаемыми document ID и остаётся диагностикой стабильности retrieval.
`source_claim_support_accuracy` проверяет, что фактически выбранный источник
релевантен intent и поддерживает обязательные тезисы ответа, а
`normative_source_accuracy` — что источник допускается для нормативного ответа
и не является примером или шаблоном. Другой действующий нормативный источник
не делает пользовательский ответ ошибочным только из-за отличающегося ID.

Offline-команда без внешних API:

```powershell
python scripts/evaluate_regulation_qa.py --offline --top-k 5 --show-failures
```

Conversation-набор из 17 многошаговых сценариев проходит через тот же
`TelegramIntakeAdapter`, который используется production wiring:

```powershell
python scripts/evaluate_regulation_conversations.py --show-failures
```

Основная offline evaluation считает hit@k, MRR, source document accuracy и
структурные показатели
grounding/refusal/citations, `answer_relevance`,
`unsupported_concrete_value_rate`, `example_leakage_rate` и
`normative_source_accuracy`. Эти показатели проверяют retrieval context и
validation contract. `answer_correctness_proxy` не является автоматической
semantic correctness текста; для неё нужен отдельный разрешённый model run и
ручная оценка.

`example_leakage_rate` учитывает использование example/template как фактически
процитированного доказательства. Нецитированный кандидат retrieval сам по себе
не считается утечкой; перенос конкретных запрещённых значений отдельно
контролируется `unsupported_concrete_value_rate` и production validation.

Отдельный `data/evaluation/regulation_qa_production_cases.json` фиксирует 20
вопросов реального smoke test: ожидаемый статус и intent, источники,
обязательные и запрещённые тезисы, необходимость уточнения и исходную причину
отказа. Для него дополнительно считаются `end_to_end_success_rate`,
`false_refusal_rate`, `clarification_accuracy`,
`general_policy_question_accuracy`, `word_number_normalization_accuracy` и
`multi_intent_answer_accuracy`:

```powershell
python scripts/evaluate_regulation_qa.py --offline `
  --cases data/evaluation/regulation_qa_production_cases.json `
  --show-failures
```

Read-only диагностика реального Supabase retrieval:

```powershell
python scripts/debug_regulation_retrieval.py "Вопрос по регламенту"
```

Скрипт показывает нормализацию, strict/text/broad представления, варианты,
semantic/lexical/hybrid кандидатов, вид источника, intent match, причину
relevance decision и финальный контекст. Он не содержит mutation-вызовов, но обращается к
реальной Supabase и создаёт query embeddings, поэтому запускается только после
явного разрешения.

Локальная диагностика post-generation validation:

```powershell
python scripts/debug_regulation_answer.py "Вопрос по регламенту"
```

Она показывает безопасную сводку структурированного результата: количество
утверждений, идентификаторы процитированных фрагментов, конкретные значения и
стабильный код сработавшего правила. Полный текст найденных фрагментов, сырой
ответ модели, prompt и секреты не выводятся. Вывод не попадает в production
journal. Команда передаёт вопрос и выбранные нормативные фрагменты в OpenAI
answer provider и поэтому требует отдельного явного разрешения.

Для разовой локальной диагностики доступен явный флаг
`--show-structured-output`. Он выводит только распарсенный DTO ответа и не
выводит prompt, request body, полный текст документов или сырой API response.

## Результат end-to-end smoke test

Regulation Q&A подключён к Telegram и проверен на реальном read-only retrieval.
Форматы `530000 руб` и `530 000 рублей` дают одинаковое нормативное решение;
сроки «10 дней», «14 дней» и «две недели» одинаково сравниваются с правилом
срочности. Вопросы о перевозке 5 и 12 паллет используют значения пользователя,
а не реквизиты учебного примера. Вопрос о текущей минимальной цене поставщика
получает контролируемый отказ из-за отсутствия таких данных в базе. Для
успешных ответов источники соответствуют использованным правилам.

## Ограничения MVP

- «Мои заявки» показывает одну страницу из пяти записей.
- Q&A не выбирает поставщика и не использует внешние данные.
- Нет reranker. Принадлежность суммы диапазону и сравнение длительности с
  нормативом вычисляются детерминированным post-processing, а не средствами
  RAG или LLM.
- При отсутствии OpenAI конфигурации intake может работать в `rule`, но Q&A
  корректно сообщает о временной недоступности.
- Ответы ограничены содержимым индексированной учебной базы и не используют
  актуальные цены, остатки или внешние каталоги поставщиков.
- Обновление вложенного pending-контекста использует client-side
  read-modify-write без compare-and-swap или версии строки. При одновременных
  изменениях `state_data` из нескольких процессов возможна потеря одного из
  конкурентных обновлений; для production-нагрузки потребуется атомарная RPC
  или optimistic locking.

# Анализ дефектов финального rehearsal-теста

Дата анализа: 10.08.2026

Статус: root-cause analysis, без исправлений

Область проверки: локальный код, тесты, evaluation-наборы и подготовленные
данные базы знаний. Внешние API, Telegram, OpenAI и Supabase не вызывались.

## 1. Executive summary

Финальный rehearsal выявил не пять независимых опечаток, а четыре системных
разрыва на границах компонентов:

1. нормализация короткого ответа и извлечение из полного текста используют
   разные грамматики;
2. разделение составной потребности покрывает только закрытый перечень предметов
   и отдельный специальный сценарий G05/S05;
3. RAG сначала принудительно присваивает вопросу один из известных intent, а
   затем проверяет ответ относительно этого уже выбранного intent, а не
   относительно исходного смысла вопроса;
4. автоматические метрики в основном доказывают прохождение фиксированных
   примеров и контрактов, но не покрывают морфологические, композиционные и
   out-of-domain переходы, обнаруженные в rehearsal.

Наиболее опасен CASE 3: ошибочная категория той же G-ветки проходит текущую
проверку полноты и может быть зарегистрирована. CASE 4 и CASE 5 показывают, что
наличие источника и формально валидной ссылки ещё не означает релевантность
ответа исходному вопросу. CASE 1 и CASE 2 воспроизводимы точными различиями
между словарями/грамматиками разных путей ввода.

Архитектуру можно стабилизировать без полного переписывания. Нужны ограниченные
изменения в общих границах: единая нормализация значений, типизированное
представление составной потребности до выбора категории, явный domain/intent
gate для Regulation Q&A и end-to-end regression-наборы через production wiring.
Продолжение точечных словарных исключений без этих границ будет лишь переносить
дефекты на соседние формулировки.

### Follow-up status CASE 1–2

10.08.2026 выполнен первый ограниченный цикл стабилизации:

- CASE 1 закрыт единым canonical unit registry для clarification parser,
  deterministic extraction и structured normalization; добавлены формы
  `пачка/пачки/пачек`, а explicit physical/packaging unit закреплена выше
  inferred `шт.`;
- CASE 2 закрыт общей amount grammar для full-expression и span-search путей;
  NBSP и terminal punctuation имеют одинаковую семантику, а диапазон scalar
  intake amount контролируемо отклоняется обеими ветками;
- исторический анализ ниже сохранён без переписывания; CASE 3–5 остаются
  открытыми и не входили в этот цикл.

## 2. Таблица дефектов

| Case | Наблюдение | Непосредственная причина | Системная причина | Риск |
|---|---|---|---|---|
| 1. `50` → `пачек` | вопрос об единице повторяется; позже возможно `50 шт.` | `пачек` отсутствует в `_UNIT_ALIASES` и `_EXPLICIT_UNIT`; неизвестное существительное после числа трактуется как счётный предмет | две несогласованные грамматики unit плюс небезопасный default `шт.` | неверная карточка и регистрация |

| 3. светильники + монтаж | теряется mixed-структура, предлагается S01 после выбора товара, затем принимается G01 | общий split распознаёт только шесть товарных паттернов; software mixed имеет отдельную ветку; category state может пережить смену типа; проверяется только префикс G/S | нет общего представления позиций/ролей и семантической проверки category–subject | критический: регистрация неверной заявки |

| 6. evaluation | все фиксированные наборы зелёные при провале rehearsal | отсутствуют конкретные переходы: падеж unit, punctuation amount, произвольный mixed, literal `черновик`, бытовой OOD | метрики преимущественно проверяют заранее типизированные ожидания и retrieval/claim proxies | ложная уверенность в готовности |

## 3. Detailed trace каждого кейса

### 3.1. CASE 1 — quantity/unit: `50` и `пачек`

#### Фактический путь

1. После ответа `50` `TelegramMessageParser._parse_value()` в
   `app/bot/parser.py` нормализует quantity в `Decimal("50")`. Значение
   сохраняется, completeness оставляет `unit` незаполненным и задаёт следующий
   вопрос.
2. Для активного вопроса `unit` тот же `_parse_value()` вызывает только
   `normalize_unit()` из `app/bot/normalization.py`.
3. `_UNIT_ALIASES` содержит `упаковка/упаковки/упаковок`, коробки, комплекты и
   формы `шт.`, но не содержит `пачка/пачки/пачек`. Exact lookup заканчивается
   `ValueError("Unsupported unit")`.
4. Если structured extraction не используется или также отклоняет значение,
   update не сохраняется. Persistence round-trip поэтому возвращает draft с
   quantity=50 и unit=null; completeness снова выбирает `unit`.
5. Отдельный путь свободного извлечения использует `_EXPLICIT_UNIT` и
   `_extract_goods_count()` в `app/bot/extraction.py`. В `_EXPLICIT_UNIT` также
   нет форм `пачка/пачек`.
6. Для конструкции `50 пачек` неизвестное слово после числа считается не
   единицей упаковки, а существительным одной счётной товарной позиции.
   `_extract_goods_count()` присваивает fallback `unit="шт."`.
7. В `merge_intake_candidates()` (`app/extraction/intake.py`) unit относится к
   deterministic authority fields. Structured `null` не стирает deterministic
   значение; structured `unit_raw="пачек"` тоже не проходит общую
   `normalize_unit()`. Проверка explicit-unit evidence опирается на тот же
   неполный словарь. Поэтому ошибочное inferred `шт.` может пережить merge и
   сохранение.

Точная точка первичного отказа — `normalize_unit()`; точка появления неверного
default — `_extract_goods_count()`. Это не проблема formatter: в карточку
попадает уже сохранённое каноническое значение `шт.`.

#### Почему тесты не поймали

- `test_piece_units_are_normalized` проверяет формы `шт/штука/штуки/штук/единиц`.
- `test_safe_goods_count_and_unit_extraction` проверяет `упаковки`, но не
  синоним `пачка` и его падежи.
- production-wiring тесты подтверждают полезный inference `шт.` для тарелок,
  лампочек, банок, клавиатур и принтера, но не проверяют переход
  `awaiting unit → морфологическая упаковочная единица → persistence reload`.
- нет инварианта: явная физическая/упаковочная мера никогда не может быть
  заменена inferred `шт.`.

### 3.2. CASE 2 — amount: `До 120 000 рублей.`

#### Фактический путь

1. Для активного вопроса суммы parser вызывает `parse_amount_expression()`.
2. Функция нормализует пробелы, но применяет full match ко всей строке.
3. Грамматика знает модификаторы `до`, `не более`, `максимум`, а также
   приблизительные `около`, `примерно`, `ориентировочно`, `порядка`. Она знает
   пробельные разряды, `тыс./тысяч`, `млн` и формы рубля.
4. После слова `рублей` допускается окончание выражения, но не отдельный знак
   конца предложения. Поэтому `До 120 000 рублей.` не совпадает из-за финальной
   точки; `не более 120 тыс руб` без точки совпадает.
5. В первом длинном сообщении применяется другой путь —
   `find_amount_expression()` с `_AMOUNT_SEARCH`. Он ищет span внутри текста и
   может закончить совпадение перед финальной пунктуацией. Одинаковое выражение
   поэтому ведёт себя по-разному в initial description и в clarification reply.

Поддерживаемые сейчас одиночные формы: точная сумма, upper-bound через `до`,
`не более`, `максимум`, приблизительная сумма через перечисленные маркеры,
масштабы тысяч/миллионов, валюта и ограниченный billing period. Диапазоны
денег реализованы отдельно в approval extraction, но не являются единым
контрактом Telegram amount parser. Это дополнительный архитектурный разрыв,
хотя он не является непосредственной причиной данного примера.

#### Почему тесты не поймали

Параметризованные тесты используют `до 120 тысяч`, `не более 120 тыс.`,
`около 120 000` и похожие значения без пунктуации предложения после валюты.
Нет матрицы вида «одна семантика × короткий ответ/полное предложение × все
разрешённые currency endings × terminal punctuation».

### 3.3. CASE 3 — mixed goods/service и category resolution

#### Trace production wiring

1. `TelegramIntakeAdapter.handle_text()` до обычного extraction вызывает
   `_start_software_scope_resolution()` и `_start_multi_category_split()` только
   при создании нового draft.
2. Software-ветка типизирована только для G05/S05. Она не применима к
   светильникам и монтажу.
3. Общая `_start_multi_category_split()` вызывает
   `extract_procurement_items()`. `_ITEM_PATTERNS` знает только компьютер,
   ноутбук, стол, тумбу, шкаф и кресло; каждый match заранее имеет
   `procurement_type="goods"`. Светильники и действие монтажа не образуют две
   типизированные позиции, поэтому split не запускается.
4. `DeterministicEntityExtractor._procurement_type()` проверяет товарные глаголы
   (`купить/закупить/приобрести/товар`) раньше service-маркеров, включая
   `монтаж`. Смешанное сообщение схлопывается в один тип, обычно goods.
5. Structured extraction может вернуть отсутствующий либо другой тип. В
   `merge_intake_candidates()` procurement_type не входит в перечень
   deterministic authority fields. Поэтому детерминированный goods не является
   безусловным итогом hybrid merge; реальный вопрос «Товар или услуга?» совместим
   с этим путём.
6. Категорийный classifier без заданного типа видит `монтаж` и получает S01.
   При заданном goods `_filter_type()` удаляет S01. Однако
   `_category_candidates()` прежде всего возвращает уже сохранённые candidates
   из `dialog_states.state_data` и не фильтрует их повторно относительно
   текущего draft.procurement_type. Это позволяет устаревшему S-кандидату
   пережить ответ «Товар» и снова показываться.
7. Источник именно того сохранённого S01 в конкретном production-сеансе нельзя
   восстановить без snapshot `dialog_states.state_data` и безопасной трассы
   structured result, которых в материалах rehearsal нет. Код подтверждает два
   возможных источника: untyped классификация слова `монтаж` или кандидат,
   сохранённый до смены типа. Это ограничение доказательности, а не предположение
   о данных Supabase.
8. `_parse_category()` при наличии candidates принимает только номер/название
   из сохранённого списка, поэтому неверный список создаёт цикл. Если candidates
   отсутствуют, exact название любой категории из `CATEGORY_NAMES` принимается
   без проверки связи с предметом. Так «Офисные принадлежности» превращается в
   G01.
9. `IntakeFieldValidator.validate_draft()` проверяет лишь существование кода и
   соответствие префикса: goods→G, service→S. S01 при goods блокируется, но G01
   при goods считается валидным независимо от того, что предмет — светильники.
10. `RequestIntakeService` после такой проверки считает draft complete,
    формирует card и ready status. Persistence сохраняет уже принятый draft.
    `RequestLifecycleService.confirm_request()` заново рассчитывает readiness,
    но использует ту же prefix-only validation; отдельной semantic
    category–subject проверки перед регистрацией нет.

Итог: persistence и lifecycle не создают ошибку, но надёжно сохраняют и
регистрируют ошибку, пропущенную extraction/category validation.

#### Почему это общий дефект

Действующая архитектура имеет:

- закрытый список нескольких goods-предметов для общего split;
- отдельный hard-coded mixed-механизм только для лицензии + установки;
- один scalar `procurement_type`, `item_name`, `quantity`, `unit` и
  `category_code` до разрешения составной потребности;
- отсутствие общего промежуточного списка «позиция/роль/тип/кандидаты»;
- отсутствие семантического gate перед readiness.

Поэтому соседние пары «оборудование + монтаж», «материалы + укладка»,
«кондиционер + установка», «товар + доставка» будут зависеть от конкретных
слов, а не от общего правила смешанной потребности.

#### Почему тесты не поймали

- `tests/test_telegram_multicategory.py` покрывает компьютер + стол и две
  позиции мебели, то есть только известные goods patterns.
- `tests/test_telegram_service_categories.py` подробно покрывает G05/S05, но
  именно через отдельный software scope.
- Blind case про «оборудование и услугу монтажа» проверяет Regulation Q&A —
  нормативный ответ о разделении, а не intake adapter и регистрацию.
- нет lifecycle-level negative теста: category с правильным префиксом, но
  несовместимая с предметом, не должна становиться confirmable.

### 3.4. CASE 4 — вопрос о сохранении черновика

Для вопроса «Можно ли начать оформлять заявку, сохранить её как черновик и
закончить позднее?» локальный query plan текущего кода формируется так:

- primary intent: `status_explanation`;
- secondary intent: `draft_and_history`;
- retrieval intents: `status`, `draft_history`;
- первый status query: `статус черновик значение переходы действия заказчика`;
- draft query: `сохранить незавершенную заявку как черновик продолжить позже`.

Причина — `_status_name()` включает литерал `черновик` в список имён статусов.
В `_intents()` status добавляется раньше draft. Корректный deterministic direct
answer существует для primary `draft_and_history`, но из-за ошибочного primary
не вызывается.

В подготовленной базе есть правильные chunks:

- `kb-010`, chunk `d4bcec85-a484-5148-b4ae-676f3894073a`, FAQ / «Можно ли
  сохранить заявку и продолжить позже?»;
- `kb-014`, chunk `a5a8c46b-31f4-58a2-aa0a-fa235c74636f`, инструкция / «Как
  сохранить и продолжить черновик».

Одновременно `kb-007` содержит два status chunks, включая
`c46cf4c3-22a5-5042-9ec0-366e89bcf297`. Так как status — первый intent,
`select_relevant_regulation_chunks()` диверсифицирует выбор начиная со status.
Фактический пользовательский источник «Статусы заявки и переходы» подтверждает,
что в answer provider прошёл `kb-007`. Точный полный список рангов и выбранных
chunk IDs прежнего production-вызова не сохранён: production log намеренно
содержит только counts/reason codes, а не тексты и IDs. Его нельзя честно
восстановить задним числом.

Validator пропускает нерелевантный ответ по двум причинам:

- `_claim_supported_by_chunk()` требует лишь одно общее значимое слово между
  claim и source;
- `_claim_answers_intent()` считает claim релевантным, если он совпадает хотя бы
  с одним из intent plan. Ответ про статус удовлетворяет ошибочно добавленному
  `status`, даже если не отвечает на вопрос о сохранении.

Похожий blind-тест есть, но фраза «Можно сохранить незаполненную заявку и
вернуться к ней позднее?» не содержит литерал `черновик`; поэтому конфликт
status/draft не возникает. Тест подтверждает соседнюю удачную ветку, а не
rehearsal-формулировку.

### 3.5. CASE 5 — out-of-domain вопрос о борще

Локальный plan для «Подскажи рецепт борща и составь список продуктов на 6
порций» имеет:

- primary intent: `required_fields`;
- outside_kb_intent: false;
- retrieval intent: `category_fields`;
- сгенерированный query про общие обязательные поля заявки;
- broad query, в котором к словам про рецепт добавлены `категория`,
  `обязательные`, `поля`, `требования`.

Это происходит потому, что `_intents()` возвращает `required_fields` для любого
текста, который не совпал ни с одним правилом. Универсального procurement-domain
classifier/gate нет. Supplier/current-price вопросы отклоняются не общим OOD
механизмом, а узким regex `_supplier_recommendation()` и direct answer для
`outside_kb`.

После неверной классификации система сама делает запрос похожим на базу знаний.
`_supports_intent()` закономерно принимает field matrix, а deterministic
category-fields fallback формирует ответ об обязательных полях. Validator снова
проверяет соответствие ошибочному `category_fields`, а не вопросу о рецепте.

Порог не защищает эту ветку:

- default `RAG_SIMILARITY_THRESHOLD` равен 0.0;
- `KnowledgeRetrievalService` передаёт threshold для semantic search;
- текущий hybrid RPC вообще не принимает similarity threshold и берёт top-N
  semantic candidates независимо от абсолютной релевантности;
- lexical candidates и intent query expansion также не имеют domain threshold.

Следовательно, наличие «похожего» нормативного chunk — ожидаемое следствие
ошибочного intent, а не доказательство принадлежности вопроса к закупкам.

#### Почему тесты не поймали

Во всех четырёх single-turn наборах outside-KB примеры сосредоточены на
поставщиках, перевозчиках, рекомендациях и текущих ценах — ровно на покрытом
regex-классе. Бытового нерелевантного вопроса, который не содержит этих слов,
нет. Conversation dataset OOD-сценариев не содержит.

### 3.6. CASE 6 — почему evaluation не отражал rehearsal

Текущие проверки полезны, но измеряют разные ограниченные контракты:

- `evaluate_regulation_qa.py` в offline-режиме прежде всего оценивает попадание
  ожидаемого document ID в top-k и вычисляет proxy-ответ; реальный semantic
  смысл пользовательского ответа там не генерируется;
- holdout evaluator использует `FakeGroundedAnswerProvider` и deterministic
  fallback, а source claim support определяется regex по expected intent и
  объединённому тексту документов;
- conversation evaluator проверяет 17 заранее заданных Q&A turns через adapter,
  но не intake и не произвольный OOD;
- intake holdout оценивает поля одного сообщения, а не полный stateful диалог,
  category loop, reload и confirm;
- production-wiring tests широко проверяют безопасный `шт.`, но не конфликт
  explicit packaging unit с inference;
- multicategory tests разделены на известные товары и специальный software
  scenario, поэтому создают видимость общего покрытия mixed category.

Наборы не объединены с rehearsal — это правильно. Проблема в том, что не было
отдельного coverage-контракта по классам риска: морфология коротких ответов,
эквивалентность initial/follow-up parsing, произвольная mixed-потребность,
семантическая совместимость категории, OOD negative controls и конфликт intents.

## 4. Общие системные причины

1. **Несколько источников истины для языка.** Unit и amount разбираются
   различными словарями/regex в parser, deterministic extractor и structured
   normalization.
2. **Scalar draft создаётся раньше разрешения композиции.** Смешанный запрос
   схлопывается в один тип и одну категорию до появления общего списка позиций.
3. **Special cases маскируют отсутствие общей модели.** G05/S05 работает
   хорошо, но не доказывает поддержку произвольного goods+service.
4. **Валидация формы вместо смысла.** Category validation проверяет prefix;
   answer validation — пересечение терминов и один из внутренних intents.
5. **Closed-world intent fallback.** Неизвестный вопрос считается
   `required_fields`, а не `unknown/outside_domain`.
6. **Query expansion усиливает ошибку классификации.** После неверного intent
   retrieval почти гарантированно находит формально подходящий документ.
7. **Метрики не имеют независимых negative controls на каждой границе.**
   Зелёный результат фиксированного набора был интерпретирован шире, чем реально
   доказанный контракт.

## 5. Минимальный scope исправлений

### P0 — до следующей регистрации rehearsal-сценариев

1. Ввести единый canonical unit lexicon/normalizer для direct answer,
   deterministic extraction и structured normalization; добавить семейство
   `пачка` и инвариант explicit measure > inferred `шт.`.
2. Сделать единый amount-expression parser для initial span и clarification,
   допускающий безопасную терминальную пунктуацию и возвращающий одинаковую
   структуру modifier/value/currency/period.
3. До записи scalar category в draft создавать общий результат decomposition:
   одна позиция, несколько однородных позиций, несколько категорий или
   goods+service. Один общий resolver должен обслуживать не только software.
4. При изменении procurement_type инвалидировать либо повторно фильтровать
   persisted category candidates. Selection всегда проверять против актуального
   type и актуального decomposition state.
5. Добавить semantic compatibility guard перед
   `ready_for_confirmation`/confirm. Для неуверенной совместимости —
   clarification, а не произвольный same-prefix код.
6. В Regulation Q&A отделить `unknown/outside_domain` от `required_fields`.
   Retrieval запрещать до положительного domain gate либо явного procurement
   intent.
7. Исправить конкуренцию status/draft: слово `черновик` в вопросе о действии не
   должно автоматически делать status primary. Финальная relevance-проверка
   должна оценивать обязательный primary intent и исходный вопрос, а не любой
   secondary intent.

### P1 — сразу после P0

1. Калибровать hybrid relevance на независимом negative set; threshold должен
   иметь однозначную семантику и реально применяться ко всем путям кандидатов.
2. Добавить безопасные диагностические IDs этапов и решений (без текста chunks
   и payload), чтобы следующий rehearsal можно было разобрать без реконструкции.
3. Разделить метрики: extraction correctness, conversation correctness,
   semantic category compatibility, domain rejection и final-answer relevance.

## 6. Что НЕ следует исправлять

- Не добавлять отдельный hardcode только для `пачек`, светильников, борща или
  точного rehearsal-текста. Нужны классы форм и инварианты.
- Не исправлять CASE 1 только formatter-ом: неверное значение уже находится в
  canonical draft.
- Не повышать вслепую similarity threshold: hybrid RPC сейчас не применяет его
  как общий барьер, а высокий порог может дать ложные отказы по корректным
  перефразировкам.
- Не расширять `_ITEM_PATTERNS` бесконечным каталогом существительных вместо
  общего decomposition contract.
- Не доверять category, выбранной LLM, без type/decomposition/compatibility
  проверки.
- Не запрещать `kb-007` и не понижать его глобально: источник корректен для
  вопросов о статусах; ошибочен intent и выбор для конкретного вопроса.
- Не ослаблять запрет example/template и concrete-value validation: эти защиты
  не вызвали рассматриваемые дефекты.
- Не менять базу знаний или embeddings для вопросов о черновике и борще до
  исправления понимания/domain gate. Правильные chunks о черновике уже есть.
- Не изменять SQL-миграции задним числом. Если relevance threshold потребует
  изменения RPC, это должна быть новая repeat-safe migration отдельным этапом.

## 7. Новые regression tests

### Unit и amount

1. Adapter-level sequence с реальным persistence repository:
   `бумага A4 → 50 → пачек → reload`; ожидать unit=`пач.`/принятый канонический
   код, отсутствие повторного unit question и отсутствие `шт.`.
2. Параметризация `пачка/пачки/пачек`, `упаковка/упаковки/упаковок`, явные
   физические меры и счётные предметы.
3. Инвариант merge: structured null не стирает valid deterministic unit;
   explicit packaging unit, подтверждённая текстом, имеет приоритет над
   inferred `шт.`.
4. Одна таблица amount cases для initial и awaiting paths: terminal `. , ! ?`,
   все формы рубля, `₽`, `тыс.`, NBSP, upper-bound и approximate modifiers.
5. Отдельно определить контракт диапазона; не позволять двум Telegram путям
   возвращать разные типы результата для одной строки.

### Mixed category и lifecycle

1. Полный adapter→persistence→reload сценарий «светильники + монтаж»:
   `split_required`, две типизированные потребности, отсутствие готовой карточки
   до выбора.
2. Аналоги без точных существительных из rehearsal: оборудование+установка,
   материалы+монтаж, товар+доставка.
3. После ответа «товар» сохранённые S-candidates должны быть удалены/пересчитаны;
   после «услуга» — симметрично G-candidates.
4. Выбор номером, названием и partial name проверяется только среди актуальных
   candidates после reload.
5. Негативный lifecycle test: same-prefix, но семантически несовместимая
   категория не становится confirmable и не регистрируется.
6. Доказать отсутствие регрессии существующих goods multicategory и G05/S05.

### Regulation Q&A

1. Парафразы draft с буквальным словом `черновик`, одновременно с глаголами
   начать/сохранить/закончить/продолжить: primary=`draft_and_history`, источник
   `kb-010` и/или `kb-014`, без `kb-007` как единственного основания.
2. Настоящие вопросы о статусе «Черновик» должны по-прежнему получать
   `status_explanation` — нужен контрастный тест, а не удаление статуса.
3. OOD negative set из несвязанных доменов: рецепты, медицина, погода, кино,
   программирование, поездки. Ожидать controlled refusal без retrieval.
4. Near-domain controls: список продуктов как предмет закупки для мероприятия
   должен отличаться от запроса рецепта; поставщик и текущая цена остаются OOD.
5. Validator regression: answer, подтверждающий только secondary intent и не
   отвечающий primary question, отклоняется.
6. Evaluation должна проверять итоговый пользовательский текст и sources через
   тот же adapter/service, а не только наличие expected ID в top-k.

## 8. Порядок исправлений

1. Зафиксировать новые failing regression tests без изменения production logic.
2. Унифицировать unit/amount normalization и закрыть CASE 1–2.
3. Ввести общий decomposition/category state и lifecycle guard; закрыть CASE 3.
4. Ввести explicit unknown/OOD intent и исправить status/draft priority.
5. Усилить final-answer relevance относительно primary intent и original
   question.
6. Пересобрать независимые single-turn, conversation и lifecycle holdouts.
7. Повторить локальный production-wiring rehearsal, затем разрешённый внешний
   smoke. Только после этого обновлять acceptance-документы.

## 9. Риски регрессии

| Изменение | Возможная регрессия | Обязательная защита |
|---|---|---|
| расширение unit grammar | предметное существительное ошибочно станет unit | negative countable nouns и explicit-unit precedence |
| terminal punctuation для amount | захват соседних чисел/дат | span boundaries и date/quantity controls |
| общий mixed decomposition | ложное разделение услуги по нескольким объектам | service volume cases: ремонт 5 кресел, сборка 3 шкафов и 2 столов |
| очистка category state | потеря корректного выбора после reload | persisted candidates + unchanged-type tests |
| semantic category guard | избыточные уточнения для редких категорий | controlled unknown/clarification и каталог реальных G01–G15/S01–S15 |
| OOD gate | false refusal для кратких закупочных вопросов | near-domain short questions и multi-turn pending context |
| приоритет draft над status | потеря настоящего статуса «Черновик» | контраст action-vs-status tests |
| строгая answer relevance | рост `unsupported_answer` | deterministic answers и model repair на независимом paraphrase set |

## 10. Документы и acceptance statements, которые теперь устарели

До повторной приёмки нельзя использовать как актуальное доказательство
готовности следующие формулировки:

1. `docs/final/ACCEPTANCE_TEST_REPORT.md`:
   - статус «MVP принят с известными ограничениями» и итоговое решение о том,
     что основные сценарии работают;
   - утверждение, что обнаруженные ограничения не блокируют демонстрацию;
   - таблица, где извлечение/уточнение обязательных полей, карточка и ответы по
     регламентам обозначены как пройденные без оговорки о новых rehearsal
     дефектах;
   - результаты 20/20, 25/25, 17/17 и 1113 passed остаются исторически верными
     для тех наборов, но больше не подтверждают текущую приёмку.
2. `docs/final/FINAL_TECHNICAL_SPECIFICATION.md`:
   - статус «MVP развернут на VPS и принят с известными ограничениями»;
   - вывод «готов к защите на заранее проверенных сценариях»;
   - `Ответы по базе знаний ... подтверждено на фиксированных наборах` нужно
     дополнить тем, что rehearsal обнаружил false relevant answer и OOD false
     answer;
   - category status `частично подтверждено` должен явно включать блокирующий
     mixed goods/service дефект и отсутствие semantic compatibility gate.
3. `docs/technical/telegram_adapter.md`:
   - описание, что реестр упаковки имеет приоритет, неполно без `пачка/пачек`;
   - утверждение об одном механизме category resolution для goods/services не
     означает общий механизм mixed decomposition: фактически arbitrary mixed и
     software mixed идут разными путями;
   - раздел «Товары разных категорий» описывает только распознаваемые
     `_ITEM_PATTERNS` и не должен читаться как универсальная поддержка;
   - список известных ограничений нужно дополнить различием grammar initial vs
     clarification, отсутствием общего OOD gate и semantic category guard.
4. Любые презентационные выводы, повторяющие «приёмка завершена», «критические
   дефекты отсутствуют» или интерпретирующие фиксированные evaluation scores как
   универсальную точность, следует считать приостановленными до исправлений и
   нового независимого rehearsal.

При этом исторические цифры тестов не нужно удалять или переписывать: их следует
маркировать как результаты конкретной версии и конкретных наборов. SQL migrations
и база знаний не являются источником выявленных intake/RAG ошибок и не должны
меняться в рамках первого цикла исправлений, кроме возможной будущей отдельной
миграции для действительно согласованного hybrid threshold.

## 11. Follow-up CASE 3 — mixed goods/service и category safety

10.08.2026 выполнен ограниченный CASE 3 без изменения схемы БД.

- До scalar intake добавлен типизированный `ProcurementDecomposition` с видом,
  двумя потребностями, evidence, category candidates, общим контекстом и
  fingerprint. Явная конструкция приобретения товара и отдельно заказанного
  монтажа/установки/укладки/сборки теперь приводит к `split_required`.
- Rehearsal-сообщение о 20 светильниках и монтаже сохраняет товар и услугу как
  разные candidates. До выбора `item_name` и `category_code` scalar draft не
  заполняются. При выборе монтажа сохраняются общий срок и адрес, но не
  количество товара.
- Отрицательные controls подтверждают отсутствие split для одной услуги с
  несколькими объектами, ремонта, перевозки, уборки и доставки поставщиком как
  условия товарной закупки.
- Persisted category candidates фильтруются относительно актуального
  `procurement_type`; смена goods/service очищает несовместимый набор и не
  позволяет выбрать старый код после reload.
- Prefix guard дополнен semantic compatibility: точный deterministic match или
  безопасный ограниченный набор блокирует очевидно чужую same-prefix category.

## Follow-up CASE 4–5 — 11.08.2026

CASE 4 и CASE 5 закрыты без изменения intake, базы знаний, embeddings, SQL и
миграций.

- Intent planner различает `known_domain_intent`, `ambiguous_domain` и
  `outside_domain`; неизвестность больше не означает `required_fields`.
- Positive domain gate выполняется до query expansion и hybrid retrieval.
  Очевидный бытовой OOD получает `outside_domain`, пустой список источников и
  `retrieval_status=not_called`.
- Supplier/current-price запросы остаются закупочно-связанным, но
  неподдерживаемым capability и получают прежний controlled refusal
  `outside_kb` также без retrieval.
- Действия сохранить/продолжить черновик имеют приоритет над буквальным
  `status_name=черновик`; явные вопросы «что означает статус» и «какие
  переходы» по-прежнему получают `status_explanation`.
- Draft action теперь ищет FAQ/user guide и формирует grounded ответ из
  найденного источника; status guide не может быть его единственным
  основанием.
- Final relevance проверяет обязательный primary intent исходного вопроса.
  Ответ, покрывающий только secondary intent, отклоняется.
- Добавлен независимый offline domain-набор с раздельными метриками domain
  classification, OOD rejection, primary intent, final relevance, source
  support, unsupported concrete values и example leakage.

Оставшийся риск: positive gate основан на ограниченной детерминированной
лексике и онтологии. Редкая закупочная формулировка без явного предметного
сигнала безопасно уйдёт в outside/clarification, а не запустит поиск; перед
пилотом требуется новый независимый paraphrase-набор и наблюдение false refusal.
  Тот же validator повторно вызывается lifecycle перед confirm.
- Специальный G05/S05 dialogue сохранён и использует тот же типизированный
  split state. Полноценный `request_items`, SQL и миграции не добавлялись.

Ограничение остаётся намеренным: decomposition обрабатывает явные action-based
конструкции и не создаёт автоматически обе заявки. Неявные составные намерения
требуют уточнения; финальная проверка не полагается только на LLM.

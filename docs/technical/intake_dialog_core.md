# Детерминированное ядро intake-диалога

## Назначение и границы

`app/intake` собирает структурированный черновик заявки по шагам. Ядро не
вызывает LLM, не сохраняет данные, не отправляет сообщения и не меняет статус
заявки в базе. Оно нормализует patch, безопасно объединяет его с черновиком,
проверяет значения и полноту, выбирает один следующий вопрос и строит карточку.

`IntakeStatus` описывает состояние диалога (`collecting`, `conflict`,
`ready_for_confirmation`) и не является `RequestStatus` из базы (`draft`,
`new`, `cancelled`). Сам intake core не выполняет переход к `new`; это делает
отдельный request lifecycle layer после явного подтверждения.

## Аудит модели хранения

Таблица `requests` уже содержит `id`, `user_id`, `request_type`,
`category_code`, `title`, `status` и расширяемый `data jsonb`. Поэтому сейчас
SQL-миграция не нужна: базовые поля могут остаться колонками, остальные поля
`RequestDraftData`, состояния значений и служебные данные диалога
сериализуются persistence orchestration в `data.intake`.

В существующем API типы называются `product` и `service`. Канонический intake
использует только `goods` и `service`; persistence mapping отображает их как
`goods → product` и `service → service`. Ремонт, монтаж, разработка и
обслуживание являются услугами и используют категории S01–S15. Старое JSON-
значение `work` нормализуется в `service` только на границе чтения persistence
с безопасным warning и никогда не создаётся новым intake update.

## Реестр полей

`RequestFieldRegistry` хранит код и подпись поля, тип, область обязательности,
приоритет вопроса, порядок карточки, валидатор, зависимости и безопасное имя
условия. Произвольный Python-код из конфигурации не выполняется. Условия
`brand_restricted`, `single_supplier`, `urgent` и
`physical_location_required` зарегистрированы в коде.

Общие обязательные поля первой версии: тип и категория, предмет,
описание/характеристики по типу, сумма и бюджетный статус, дата и обоснование
потребности. `title` необязателен: заголовок карточки берётся из явно заданного
`title`, затем из `item_name`, затем из названия категории; последний fallback
— «Заявка на закупку». Сформированный заголовок не записывается обратно в
draft. Для товара обязательны количество и единица. Место обязательно для физических товаров (кроме цифровых лицензий
G05) и услуг с подтверждённым `work_on_site=true`; удалённые услуги его
не требуют. `False` является заполненным boolean-значением; только `None`
означает отсутствие.

Подразделение и контакт — readiness-поля профиля. Они блокируют финальную
готовность, если отсутствуют, но имеют последние приоритеты вопросов и обычно
поступают с `source=system` без ручного диалога. Такое значение не считается
явно подтверждённым пользователем, но не перезаписывается менее надёжным
extraction; прямой пользовательский ответ или явная коррекция продолжают
работать по общим правилам merge.

Категорийные правила основаны на действующей базе знаний:

- G03 требует характеристики, количество, единицу и ответ о допустимости
  аналогов; при запрете аналогов и указанном бренде требуется обоснование;
- S11 требует описание состава услуги, объём/характеристики, ожидаемый
  результат и срок, но не требует количества;
- S05 требует явного ответа о доступе к данным;
- названия G02, G03, G05, S05 и S11 берутся из классификатора и показывают,
  как реестр расширяется без изменения алгоритма.

## Merge и конфликты

Приоритет источников централизован. Результат OpenAI или rule extraction
сохраняется как `source=extraction, confirmed=false`: это предварительное
предложение, а не утверждение пользователя. Прямой ответ на текущий
`next_question` помечается `source=user, confirmed=true` и без конфликта
заменяет предварительное значение. Профильное `source=system` также не выдаётся
за пользовательское подтверждение и защищено от перезаписи extraction.

`None` и пустая строка не стирают заполненное поле. Совпадающий ответ переводит
предварительное значение в подтверждённое без лишнего изменения. Отличающееся
значение без `explicit_correction=true` создаёт
`value_change_requires_confirmation` только для ранее подтверждённого
пользовательского значения. Дополнительное условие для `specifications` или
`desired_result` объединяется с имеющимся текстом с нормализованной защитой от
дублей. Ответы `подтвердить`/`изменить`/`применить` принимают предложение, а
`оставить`/`не менять` сохраняют прежнее значение; разрешённый конфликт
удаляется по его идентификатору идемпотентно.

Предпочтительный бренд не означает единственного поставщика. Имя поставщика
также не включает этот признак автоматически. Обоснования требуются только при
соответствующих явных условиях.

## Полнота и следующий вопрос

`RequestCompletenessService` детерминированно возвращает обязательные,
заполненные, отсутствующие, некорректные и заблокированные поля. Коэффициент
полноты информационный. `NextQuestionSelector` сначала обрабатывает конфликт,
затем выбирает одно поле по стабильным `priority` и `display_order`. Boolean и
choice-вопросы содержат варианты ответа. Начальный порядок: тип закупки,
понятный предмет, описание для услуги/работы, затем выбор категории по коду и
названию; пользователь не обязан самостоятельно знать код классификатора.

После категории собираются количество и единица для товара, характеристики и
категорийные поля, сумма, бюджетный статус, срок, физическое место и
обоснование потребности. Условные дополнительные поля следуют после основных
данных. Подразделение и контакт задаются последними, если профиль их не дал.

Заполненный `category_code` считается валидным только при positive support от
deterministic classifier или strong candidate с сохранённым provenance. Weak
generic fallback не является доказательством совместимости и не переводит
черновик в `ready_for_confirmation`; тот же invariant повторяется lifecycle при
confirm.

Для коротких ответов на readiness-critical free-text вопросы применяется
ограниченная deterministic compatibility-проверка. Очевидное описание цели,
места или даты не записывается как подразделение; аналогичные явные mismatch
блокируются для контактного лица и места поставки/оказания услуги. Значение не
переносится в другое поле автоматически: поле остаётся missing, а вопрос
повторяется с безопасной подсказкой.

### Пример G03 с пустого черновика

`python scripts/demo_intake_dialog.py --from-empty` начинает с пустой
`RequestDraftData`, добавляет подразделение и контакт из системного профиля и
последовательно отвечает на вопросы о 10 мониторах Samsung. При запрещённых
аналогах появляется отдельный вопрос об обосновании бренда. Текущий честный
результат — 13 вопросов до `ready_for_confirmation`; ответы первого сообщения
в реальном интерфейсе смогут заполнить несколько полей одновременно, но demo
искусственно не сокращает правила полноты.

## Approval и карточка

Существующие `ApprovalContext`, `ApprovalExtractionResult`,
`ApprovalRouteResult` и `ApprovalRuleService` переиспользуются. Контекст
создаётся, когда известны непротиворечивые `amount` и `budget_status`.
Дополнительные признаки передаются при наличии. Для диапазона или конфликта
суммы/бюджетного статуса контекст не создаётся и rule engine не вызывается.
Маршрут может быть рассчитан до полной готовности заявки.

`budget_status=unknown` является явным заполненным ответом, поэтому completeness
может довести intake до `ready_for_confirmation`. ApprovalContext при этом
создаётся, но rule engine возвращает `needs_clarification`, warning и пустой
список согласующих: неизвестный статус нельзя подставлять в бюджетную или
внебюджетную ветвь.

Карточка появляется только при полной валидной заявке без конфликтов. Она
состоит из стабильных секций, хранит структурированные поля, форматирует деньги
только для показа и удаляет дубли согласующих.

Поле карточки `amount` может содержать необязательное структурированное metadata
`amount_modifier` и `billing_period`. Источником служит evidence канонического
`field_states.amount`, которое сохраняется вместе с intake draft в JSONB.
Старые draft и карточки без metadata остаются совместимыми: отсутствие периода
означает разовую сумму, а отсутствие модификатора — `exact`. Новая колонка БД
для этого не требуется.

Hybrid Telegram pipeline сначала детерминированно выделяет ограниченные spans
суммы, даты и периода, затем получает смысловые кандидаты общего structured
extractor. Merge защищает однозначные числовые значения. Structured extractor
только предлагает факты: validators, completeness, следующий вопрос и
ApprovalContext остаются детерминированной ответственностью ядра. В `rule`
неоднозначный текст по-прежнему не подвергается свободной NLP-интерпретации.

## Локальные интерфейсы

- `GET /api/v1/intake/health`;
- `POST /api/v1/intake/evaluate-step` — без persistence и side effects;
- `python scripts/run_intake_step.py --draft ... --update ... --json`;
- `python scripts/show_intake_registry.py --all` — аудит реестра без сети;
- `python scripts/demo_intake_dialog.py` — компактная демонстрация;
- `python scripts/demo_intake_dialog.py --from-empty` — полный сценарий G03.

## Связанные и следующие этапы

Persistence orchestration, request lifecycle и Telegram adapter реализованы
отдельными слоями: ядро само не регистрирует заявку, не присваивает номер и не
формирует Telegram markup. Production E2E и генерация RAG-ответов остаются вне
этого backend milestone.
